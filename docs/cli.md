# CLI

This page lists every `compose` command and its flags.
The team lead runs them for you, and you run them yourself only in manual mode.

Run `compose` with no command on a terminal outside herdr to open the herdr session `compose` ([herdr.md](herdr.md)).
Every command takes `--repo <path>` (default `.`) and `--project <name>`.
`--project` works from any checkout of the repository.
You can leave it out when the repo has one project.

## Normal mode

Open Claude Code in the repo and run:

```
/compose plan and build <feature> from ENG-123 and DESIGN.md
```

The team lead runs every command below for you.
You review the plan, the task list, and the stack.

## Manual mode

1. Run `compose init --project my-feature`, then work in the worktree it prints.
2. On Linear, write the feature issue (its description is the plan) and one task issue per task.
   End each task issue with a [`compose` block](tasks.md).
3. Write `{"feature": "ENG-123"}` to `.compose/my-feature/linear.json`, write each task's test, and commit.
4. Run `compose sync --project my-feature`, and run it again after any Linear edit ([shape](tasks.md#sync)).
5. Run `compose run --project my-feature`, then `compose verify --project my-feature`.

When you ask, `compose stack --project my-feature --submit` pushes and opens one draft PR per layer.
After the PRs merge, `compose clean --project my-feature` removes what merged, moves those tasks to Done in Linear with their story and the feature, and keeps what did not merge.
A kept branch is named with its first unmatched commit.

Before the first run in a new repo, do these three things:

- Commit everything, because `run` refuses a dirty tree.
- Fill `verify.json` with the repo's lint and test commands ([verify.md](verify.md)).
- For OpenCode tasks only, add an `opencode.jsonc` allowing `edit` and `bash` so it never blocks on a prompt.

## Commands

### Projects

These commands create, list, and clean up projects.

| Command | Does |
|---|---|
| `setup` | Installs and configures everything `compose` needs ([new-machine.md](new-machine.md)). On a terminal it asks one question at a time (Quick start or Custom, a yes or no per missing step under Custom, each key with hidden input); `--yes`, or no terminal, runs the same steps with every default and never prompts. With `--dry-run` it asks the same questions and runs the same checks but changes nothing on the machine, prints each change as a `would` line, and ends with `dry run: nothing changed; N changes listed above`. It shows the Claude Code permission rules `compose` needs (`gh pr view`, `compose land`, moving a `compose/*` branch) and writes them to `~/.claude/settings.json` only on your yes; `--yes` and a dry run never write them, and rules that stay asking (`git push`, force-push, `gh pr merge`, `clean --delete-unmerged`, `clean --abandon`, `crew stop --force`) are never added. It exits 1 when Claude Code is missing. Without `--yes` it also exits 1 when a required key is missing or the model probe fails. With `--yes` it exits 0 and ends with `compose is installed but not ready:` when a required step is missing |
| `update` | Pulls the checkout with `--ff-only`, relinks the CLI, the skill, and `bp`, and runs `doctor`. It stops, naming the project, while a run or verify is live on this machine (`--force` updates anyway), and when the checkout has local changes. When the branch has commits its upstream lacks (a toolsmith's commits made in the installed copy), it rebases them onto upstream itself, dropping the ones already there; if the rebase conflicts it aborts it, lists each commit as `-` (already upstream under another hash) or `+` (only here), and prints the one command that gets it moving again: `reset --hard` when every one is `-`, else `rebase`. Commits only the checkout has stay there: put them on a branch and open a PR |
| `doctor` | Checks every setup step (the tools, links, keys by presence only, pi's provider, the herdr config, the skill files). It prints one `MISSING: <name> (install: <command>)` line per absent or too-old step and exits 1 when a required one is missing; the default-on steps print `- optional`, and the designer rows print one `designer extras not set up` line. While `claude` is missing, the steps that need it share one `waiting on Claude Code` line. It also warns about a key still in `config.json` or `.env`, and about a gh that is not logged in (`gh auth` is also a required step, so that is a `MISSING` line too). A `MISSING: Claude Code permissions: <rules> (install: compose setup) - optional` line lists the permission rules not yet in `~/.claude/settings.json`, because without them Claude Code's permission layer asks before `compose land`, `gh pr view`, and a `compose/*` branch move. It then runs the preflight that `run` and `verify` repeat at their start: a `PROBLEM: <what>; <fix>` line for an OpenRouter or Linear key its service rejects (a free key-info call, never a model call; an unreachable service is only a warning) and, with `--project`, for uncommitted changes `run` would refuse on; a `WARNING` line for a Mac on battery (closing the lid sleeps it), a 5-minute load average above twice the cores (naming the busiest process), and a docker container that keeps restarting (only when docker is installed and running). A problem exits 1 too. `COMPOSE_NO_PREFLIGHT=1` skips the key calls, the gh check, and the machine warnings (offline work). `init` runs the same check first and stops before creating anything only when a required tool is missing, and `designer` checks Framelink first and stops before printing a brief |
| `init` | Creates branch `compose/<name>` from the branch you are on, its worktree, and `.compose/<name>/`, and records that branch as `review_base`. `--here` uses this checkout, and `--after <project>` branches from another project (an existing project moves onto it while it has no commits of its own and a clean worktree, agent wiring aside, and is refused otherwise). Run inside herdr it also opens the project's herdr space, or its `<slug> shell` and `<slug> status` tabs in the space it was started from ([herdr.md](herdr.md#layout)); `COMPOSE_NO_HERDR=1` skips them, so a throwaway repo leaves your herdr workspace alone |
| `projects` | Lists every project with done/total, last activity, title, and states, and each line ends with its `can start now:` line |
| `status` | Shows every project with every task, each with the `can start now:` line from `results/ready.json`. `--watch` redraws every 2 s, and asks git only when a result file or a branch changed. `--digest` prints one line per project instead (tasks done, failed ids, run, last verify and why it failed, a halt, questions waiting on the product owner). `--history [N]` prints the last N lines (default 40) of the run history instead: every run start and end, task result and verify round of this repository, kept in `~/.compose/history.jsonl`. `compose cost` totals the run providers' tokens across every run in it, where `results/run-cost.json` holds only the latest run |
| `clean` | Drops merged layers, moves the tasks proven merged to Done in Linear and rolls their story and the feature up, refreshes the `Ready` marks, and removes a fully merged project's worktree and branch, or keeps them while the command runs inside the worktree or the team lead has not reported done (its `done` removes them). A branch is merged when it is contained in the target, when every commit has its patch there, when merging it would change nothing, or when GitHub has a merged PR for it; the review base is checked first. A kept branch is named with its first unmatched commit. `--delete-unmerged` also drops unreviewed layers. `--abandon --project <slug>` is the only way to remove an unmerged project: it lists what it removes (the worktree with its results and uncommitted changes, task, layer, and project branches, stack and test worktrees, herdr tabs) and what it keeps (Linear issues, branches pushed to a remote, PRs, the main checkout), then removes the worktree (returned to the treehouse pool when it is a slot) and the local branches. It refuses while a run is live or when run from inside the worktree, and while teammates are working unless `--force`; `--dry-run` lists and removes nothing |
| `trail` | Sets trail up again in the project's worktree |

### Tasks

These commands load the tasks, dispatch them, and steer the run.

| Command | Does |
|---|---|
| `sync` | Stores the feature and its task issues, read from Linear with the workspace's key, and refreshes the `Ready` marks; `--stdin` reads JSON from stdin instead. A task issue's `## Evidence` section is the CLI's and stays out of the task body. A task blocked by an unfinished issue outside the feature's tasks is listed with `waits on <id> (<state>)`, and `run` holds it |
| `linear <verb>` | Reads and writes Linear with the workspace's key and prints compact lines: `get <id> [--body] [--comments]` (`--body` ends with each heading's section hash), `list --parent <id>` or `--search "<terms>"` (with `--state`, `--label`), `create --title ... [--parent] [--label] [--state] [--priority] [--blocked-by]`, `update <id>` (`--title`, `--state`, `--parent`, `--label`, `--priority`, `--blocked-by`, and `--section "<heading>"`, `--append`, or `--description` for the body; `--section` replaces that section, from its heading line to the next heading of the same or a higher level, so an H2 takes its H3s and an H3 leaves its siblings, renames it when the body starts with another heading of that level, and removes it when the body is empty; `--expect <hash>`, the hash `get --body` listed, makes a `--section` write exit and write nothing when the section changed or went since that read; `--file` without a body flag, or no change at all, exits instead of printing `updated`), `comment <id>`, `labels [--create <name>]`, `project` (`--body` prints its description and section hashes; `--section`, `--append`, or `--description` write it), and `doc create --title ...`, `doc list`, `doc get <id>`, or `doc update <id>` (`--title`, and the same body flags and `--expect` as `update`; `doc get` prints section hashes too). Bodies come from `--file <path>` or stdin. `list`, `create`, and `doc list` use the project in `.compose/linear.json`, the one file in the repo's main checkout that every worktree of the repo reads; `get`, `update`, `comment`, and `doc update` refuse an issue or document in another project unless `--any-project`. `get` serves the same issue of the same Linear project read again within 30 seconds from `~/.compose/linear-get` (a stderr line says so), so a looping teammate cannot spend the workspace's shared hourly budget; `--fresh` reads Linear again, and `create`, `update`, and `comment` drop the cached reads. `--priority` is `none`, `urgent`, `high`, `medium`, or `low`, or Linear's 0-4. `--json` prints the raw fields. `LINEAR_URL` replaces the Linear GraphQL endpoint for the CLI's Linear calls (the e2e fake server uses it) |
| `tasks` | Prints the task list to review, with files, `after`, and tests. It warns on shared files and on a task that names a file another task owns without an `after` on it, and exits 1 after a `WARNING SERIAL CHAIN` |
| `route` | Routes each code task: a workflow (`test-first`, `implement-then-test`, `fix-then-regression-test`, or `check-only`) and a depth (`FAST`, `STANDARD`, or `DEEP`). Project policies with globs that match the task's files come first and raise the depth to `DEEP`; Jev answers the rest. A task with a protected test and no Bug label is `test-first` by that rule, with no workflow question. Each Jev answer that stays below the confidence threshold after the one retry falls back on its own (the workflow to `test-first`, the depth to `STANDARD`) and a confident answer stands; a policy answer that is unsure still raises the depth to `DEEP`, and when Jev cannot answer at all both fall back. The reason names each answer that fell back. A `route:` pin in the task's compose block fixes the workflow. It prints one line per task, `<id> <depth> <workflow>  <reason>`. With a Linear key it also writes the result as the CLI's `## Route` section on the task issue and posts it as a comment. A task whose context is unchanged since its recorded route is reused (`reused`); `--recalculate` routes it again, and `--only 003,004` limits the tasks. It exits 1 when the policies cannot be read, and records nothing then; the message names the fix (the `.compose/linear.json` to write, or the `compose linear project` check) and `COMPOSE_NO_POLICIES=1`, which reads no policy, records no route on Linear, and routes with Jev alone. `run` holds every task the same way, with the same message, until the policies are readable or `COMPOSE_NO_POLICIES=1` is set |
| `quick <id>...` | Pins `route: check-only` on small work whose result shows by running it, then routes the pinned tasks. Each id is a task id, a task's or story's Linear id, or the feature's id (all its code tasks); a story names its tasks. The pin is written into the task issue's compose block on Linear and the sync cache, and a `route:` line already there is replaced. It skips, with one `<id> skipped: <why>` line each, a task that is no longer `Todo` or `Backlog` (already dispatched), one with a protected test, one that a project policy's globs apply to, and an id that names nothing (`no such task`). Pinned tasks print `<id> pinned check-only` in task id order, then go through `route` once. A check-only task gets depth `FAST` unless its route was already recorded, runs without writing a regression test, and records its red check as `skipped (check-only)`. It exits with an error and writes nothing when the workspace has no Linear key. When the policies cannot be read, Linear fails a call, or a task's issue has no compose block, it exits 1 with one `quick: ...` line that names the task; tasks pinned before that call stay pinned and the line says to route them with `compose route --only` |
| `run` | Dispatches tasks. The flags are `--only 003,004`, `--attempts 3`, `--parallel N` (default `parallel` in the config, else 3), `--redo`, `--no-stack`, `--trunk <branch>`, `--unproven`, and `--force`. Before it clones anything it asks OpenRouter how much credit the key has left when a task runs on an OpenRouter model, and stops with the numbers and the top-up link when that is less than the dearest `--parallel` tasks are estimated to cost (the mean of the model's latest finished tasks, else $0.25 each); `--force` starts anyway. When `verify.json` has e2e cases and the stack holds no layer yet, it first refuses unless `verify --prove` passed on exactly those cases and their `e2e_setup` and `e2e_env` (`results/prove.json`); `--unproven` runs anyway. Before anything is cloned it runs the doctor preflight and stops with every problem at once, each with its fix: uncommitted changes in the project worktree (named), an OpenRouter or Linear key its service rejects, and, unless `--no-stack`, a gh that is not logged in. A session hook's rewrite of `.claude/settings.json` or `.claude/settings.local.json` and the tools' own `graft/`, `.trail/`, `.compose/`, and `.ignore` do not count as changes. A Mac on battery below 30% stops it, naming the charge and the override (`--force` starts anyway, `COMPOSE_NO_PREFLIGHT=1` skips the check). Load and crash-looping container warnings print and the run goes on. While it works, the Mac is kept awake with `caffeinate -dims -w <pid>` (macOS only, ends with the run). It records each task's red check, attempts, and outcome as evidence on the task's Linear issue ([verify.md](verify.md#evidence)); `--redo` mints a new run id per task, so earlier evidence stops counting. `--only` beside a live run on the project hands its tasks to that run (`<id> queued`) instead of starting a second one. A task that run already ended without passing is handed over again, one that passed there is kept, and one it still has pending or running makes the command print `<id> waits   for the live run (pid N)` and wait until the run ends it, then decide the same way; if the run ends first it stops with the line to start it again |
| `done` | Records tasks finished by hand with `--only <ids> --note <why>` and moves them In Review on Linear. It first writes a `done` evidence event on the task's issue: while that is not saved on Linear it marks nothing done, prints `<id> not done: its done event is not saved on Linear; run compose done again`, and exits 1 after trying every id |
| `triage` | Has a fast model clean or flag each passed task (`run` ends with it) |
| `resume` | Continues a run or verify that stopped on a billing halt. `--parallel N` sets tasks at once (default `parallel` in the config, else the halted run's). It makes the same preflight and keeps the Mac awake like `run` or `verify`; `--force` skips the same credit check as `run` and starts on a battery below 30% |
| `reflect` | Screens the settled decisions against evidence with Jev, using `--evidence -` and `--against "<line>"`. `--dismiss "<why>"` marks the evidence so far as answered, so later screens skip it |
| `hold` | Holds tasks back from dispatch with `--only <ids> --reason "<why>"`. A task the run is still preparing (clone, base, install) goes back to pending before its first turn; one already running finishes. `--release <ids>` or `all` releases them |
| `change start\|done\|undo` | Records a change of course. `undo C<n>` puts back what it touched |
| `spec-check` | Prints one `PASS|FAIL <id> <level>: <gaps>` line per issue of a feature's tree. A task fails when its brief names a file another task owns and it has no `after` on that task. `--stdin` reads sync JSON with no project. A task whose `scenarios` block lacks a required key, or whose scenario ids do not match its criteria, fails too. Exits 1 on any FAIL |
| `ready` | Labels `Ready` each story, and each feature of the epic, that is Todo or Backlog with every blocker Done or Canceled (a Design blocker counts at In Review); it writes `results/ready.json` and prints `can start now:`, and `compose linear labels --create Ready` creates the label. `sync`, the end of `run`, a `verify` PASS, and `clean` refresh the marks too |
| `bench` | Runs a frozen task set across models and reports pass rate, attempts, p50/p95 time, and cost. `--tests --base <rev>` measures test writers instead: each model writes each protected task's test from `<rev>`, and the test is scored (green on the task's files, red on `<rev>`'s, lines against the budget, cases, holdouts); it prints one summary row per model and saves `results/bench-tests-<ts>.json` |

### Verify and stack

These commands check the finished work and turn it into a stack.

| Command | Does |
|---|---|
| `verify` | Runs the local pipeline. `--fix 0` reports only, `--skip-e2e` and `--skip-review` skip those stages, and `--fresh` runs every check even where it is already green on the same tree ([verify.md](verify.md)). It first checks the keys and warns about the machine like `doctor` (a dirty tree does not stop it; a Mac on battery below 30% does, unless `--force`), and keeps the Mac awake with `caffeinate -dims -w <pid>` for the whole verify. `--prove` and every stage record evidence on Linear ([verify.md](verify.md#evidence)); while a row is unsaved it prints `verify FAIL  evidence not saved on Linear: <ids>` and exits 1. When Linear cannot record or read a task's route it prints `verify FAIL  route not recorded for <id>: <why>` and, in the line after, the fix and `COMPOSE_NO_POLICIES=1`, which skips the route catch-up; before the first stage it exits 1 |
| `stack` | Cuts passed task branches into review layers (`review_layer_lines` in verify.json, default 300 lines, groundwork and each task's tests included), at most `max_stack_prs` layers, and registers them as one gh stack on the real base. `--submit` pushes and opens one draft PR per layer, after running verify.json `checks` (not e2e) on each layer's own tree (the top layer runs every check, a lower layer only the cheap ones, the checks that are not a whole test suite, and the `test` of the tasks it is the lowest layer for: the lowest one that holds the task's code and all its test commits; a test that already fails on the stack's base and that the stack does not touch is reported and accepted) and refusing, naming the failing layer, with nothing pushed (a layer that passed is not run again, and a command already green on a layer's tree is taken with a `not rerun` line; `--fresh` runs everything), and it stops while the base is ahead of its upstream. `--submit` is incremental: it submits the layers below the first task that has not passed (`passed`, `already_green`, `hand_done`, or Done on Linear), prints a `stack  hold` line naming that task and the ones after it, and rebuilds them into the stack at the next `--submit`; with nothing below the first held task it stops with `nothing to submit`. A layer whose PR is already open and whose tip changed since (its own files changed, or a layer below it or the base moved) refuses the submit with nothing pushed, naming the layer and the cause; `--update` with `--submit` pushes it instead, with `--force-with-lease` on the PR head, and prints a `submit update` line. After a partial land the layers above the merged ones are cut on `origin/<base>`, fetched on its own (the local base is also moved to it, unless a checkout holds that branch, which is never moved), and `stack  landed` names them; when origin's base cannot be fetched it stops with nothing built or pushed; without it, each layer's PR title and body are printed, each marked `written` (from `.compose/<project>/pr/<name>.md`) or `generated` |
| `top` | Checks out the stack top for manual testing. `--detach` releases it |
| `reword` | Lists the stack layers' commits with the ones that break the commit rules flagged. `--set <sha>=<message>` (repeatable) rewords a commit and rebuilds the layers in the CLI's worktree, keeping each layer's branch; `--as-is` takes a message the rules refuse. The choice stays with the commit through later rebuilds. It never pushes: a layer that already has a PR gets the new commits with the next `stack --submit` |
| `land` | Merges the submitted stack bottom up with one `gh pr merge` per PR (`--method squash` by default, or `merge`, `rebase`; `land_method` in verify.json), waits up to `--timeout` minutes for each PR's required checks, then rebases the next layer onto the base, retargets its PR, and pushes it with `--force-with-lease`. A PR that is in a GitHub stack (`gh stack`) cannot be merged that way: it is merged through the asynchronous merge API at its current head with the same method and polled until GitHub is done, and the next layer is neither rebased, retargeted, nor pushed, because GitHub moves it onto the base itself. It merges and pushes on GitHub, so without `--yes` it only prints the plan. A stack with only some layers submitted lands those, the ones below the first layer without a PR: the plan line says `N of M layer(s) submitted`, and the `land   left` line afterwards names how many were not, which rebuild on the base at the next `compose stack --submit`. A layer with no pull request stops with `has no pull request`, and a `gh pr view` that itself fails (no network, not logged in) stops with `gh pr view failed for <branch>: <gh's last error line>`, so a PR that exists is never reported as missing. A stop names the PR and a re-run resumes. Run it only when the user said to land the stack |

### Teammates and supervision

These commands start the teammates, collect their reports, and supervise the team lead.

| Command | Does |
|---|---|
| `crew start\|list\|focus\|stop` | Manages teammates, the Claude sessions in the project's herdr space ([herdr.md](herdr.md)). `start` and `stop` from a session other than the project's live engineering manager refuse unless `--takeover`. `start` stops on a Mac on battery below 30% unless `--force` |
| `explore`, `wayfinder`, `groundwork` | Prints that teammate's brief. `--extra -` appends notes from stdin |
| `planner` | Prints the planner teammate's brief. `--issue NEB-xxx` picks the ticket, default the project's feature. `--extra -` appends notes from stdin |
| `designer` | Prints the designer teammate's brief. `--figma <url or key>` stores the Figma file key, and `--extra -` appends notes from stdin |
| `designcrews` | Starts one `design-NNN` builder for only the design tasks whose blockers are In Review or Done, and prints `<id> waits on <ids>` for the rest. `--only <ids>` picks tasks, `--max N` caps builders started at once (default `design_concurrency` in verify.json, else 3, never `parallel` in the config; the rest are printed), and `--print` prints the briefs |
| `figma check\|tree\|judge\|publish` | `check --figma <url or key>` stores the target file key in `linear.json` and proves Framelink reads the file (one depth-1 fetch; it prints the token file path and the `claude mcp add` line when it cannot). `check --plan <whoami's tier> [--pages N\|unlimited] [--modes N\|unlimited] [--need-pages N]` also stores the plan's limits as `figma_caps` (Starter: 3 pages per file, 1 mode per collection, no library publish; `--pages` and `--modes` replace the tier's predicted limit with what the designer's probe measured), prints them with the file's page count, and exits 1 with BLOCKED lines and the one upgrade-or-design-around card when the design needs more than the plan allows (the design system always needs 2 modes); `designcrews` then refuses tasks that name more pages than allowed. `publish --library <url or key> [--keys <component keys>]` is the check before asking anyone to publish a library: it reads the library's published components, component sets, and styles and its last edit through the Figma REST API (the Framelink token; it needs the `library_content:read` scope) and prints `publish: none` (nothing pending: do not ask), `publish: open` (an ask is out and the publish has not shown yet: do not ask again), or `publish: ask` (a needed key is unpublished, nothing is published, or the file was edited more than 2 minutes after the last publish; it records the one open ask in `linear.json`). A plan that cannot publish a library says `none`, and an unreadable library exits 1 with `publish: unknown`. `tree --only NNN --node <ids> [--depth n] [--bindings <file or ->]` fetches the nodes through Framelink into `results/NNN.tree.txt`, each node self-contained (Framelink's shared templates and styles inlined, an instance's variant properties and component set name added, and the hidden slots Framelink drops from instances put back with `"visible": false`), and appends what the write script returned; it names the main components missing from the tree, whose instances cannot show hidden slots. `judge --only <ids>` asks Jev MET, NOT_MET, or UNCLEAR per acceptance criterion on that tree, confirms each NOT_MET, and exits 1 on a confirmed one |
| `testcrews` | Runs one test-writing teammate per task, in parallel, at most `parallel` from the config at once when it is set |
| `toolsmith` | Prints the toolsmith teammate's brief from the project's newest tool-bug entry. The maintainer's variant files, then fixes on a branch in its own worktree of the compose repo and opens a PR with `tool-bug pr`, never committing on main of any checkout or in `~/.compose/src`; anyone else's only reproduces, diagnoses, and files. It exits non-zero when the project has no entry |
| `tool-bug file --body <file>` | Scrubs the body file (line 1 is `# <command>: <symptom>`), searches open issues on prodoxx/compose, then posts a `bug` issue or comments on the match (`--comment <n>`, or `--new` to force a new issue), and records the URL in `tool-bugs.jsonl` as `issue` on the entry `--entry "<at>"` names: the project's own, else the one of any project at that time, else the one within 2 seconds of it (it says which it used); with several candidates it refuses before posting and lists them. Without maintainer rights or a logged-in gh it saves a draft under `~/.compose/tool-bugs/` and posts nothing until the same command runs with `--approved`. A toolsmith (`COMPOSE_ROLE=toolsmith`) running it from the installed copy or a main checkout of the compose repo is refused |
| `tool-bug pr --worktree <path>` | The maintainer's machine only: pushes the branch checked out in the toolsmith's own worktree of the compose repo and opens a PR on prodoxx/compose (`--title`, default the first commit's subject; `Fixes #n` from the entry's issue), recorded in `tool-bugs.jsonl` as `pr` on the entry `--entry` names, matched as for `tool-bug file` (several candidates refuse before the push). It refuses a worktree that is the installed copy, a main checkout, or on main or master, uncommitted changes, and a branch with no commit past `origin/<default>`. The product owner merges the PRs, in one batch, when no run or verify is live |
| `report` | Lets a teammate report up with `working`, `needs-user`, `blocked`, `done`, `tool-bug`, or `contradiction`. A team lead's `working` report ends `parallel: started <what>; can start now <what>` or `parallel: none because <reason>`; `report` says so when it does not. A `needs-user` that names a Lavish page must carry the one `url:` `lavish-axi <file>` printed: `report` checks that it answers and is not given in two host forms, and adds that the product owner may answer in text. A `needs-user` for `<n> cards <ids>` is sent once: cards still unanswered are not asked again (one `reminder: ` line is allowed), and cards already in the map's Decisions so far are dropped. Asked cards are kept in `results/asked.json` |
| `watch` | Blocks until something happens (keeping the Mac awake while it waits), prints one event line, and exits. `--now` prints the current state and marks it seen, starting with `event away=on ... by=<the session that set it>` under away, or `event yolo=on ...` under yolo. An engineering manager session never wakes on a teammate another live session started unless `--from` names it. `event ready=<ids>` lists only the issues that just became ready. It has no timeout by default (`--timeout` sets one), a task starting is not an event, a teammate's plain `working` report waits for the next wake (at most 5 minutes), and a burst of events is one wake (`--settle`). ## Results

Everything a run produces lands in `.compose/<project>/results/`.
Each task run writes `.compose/<project>/results/NNN.json` with every attempt's test output, timing, and cost.
Verify writes `results/verify.json`.
A run that dies shows as `interrupted` in `status`.
A check-only task whose check already passes shows as `already_green`, whether or not it has a branch, and counts as done.
`resume` re-runs what did not pass and keeps passed layers.
`run`, `verify`, and `resume` work in their own session and write `results/<command>.log`.
The next run overwrites `run.log`, `run.json` and the result files, and returning a worktree deletes them, so every run start, run end, task result and verify round is also appended to `~/.compose/history.jsonl`.
A line holds the time, project, repository, kind, and for a task its id, model, attempts, duration, cost and outcome, and for a run's end the calls and tokens per provider: never a prompt, a log or a secret.
It survives `crew stop`, a returned worktree and a rerun; `compose status --history` reads it and `compose cost` totals every run from it.
The terminal that started one only streams that log.
Closing that terminal, or a crashed Claude session, leaves the work running.
Ctrl-C stops it.
