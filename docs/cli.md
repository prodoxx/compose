# CLI

This page lists every `compose` command and its flags.
The team lead runs them for you, and you run them yourself only in manual mode.

Run `compose` with no command on a terminal outside herdr to open the herdr session `compose` ([herdr.md](herdr.md)).
Every command takes `--repo <path>` (default `.`) and `--project <name>`.
`--project` works from any checkout of the repository.
You can leave it out when the repo has one project.

## Normal mode

Open Claude Code in the repo and run:

```
/compose plan and build <feature> from ENG-123 and DESIGN.md
```

The team lead runs every command below for you.
You review the plan, the task list, and the stack.

## Manual mode

1. Run `compose init --project my-feature`, then work in the worktree it prints.
2. On Linear, write the feature issue (its description is the plan) and one task issue per task.
   End each task issue with a [`compose` block](tasks.md).
3. Write `{"feature": "ENG-123"}` to `.compose/my-feature/linear.json`, write each task's test, and commit.
4. Run `compose sync --project my-feature`, and run it again after any Linear edit ([shape](tasks.md#sync)).
5. Run `compose run --project my-feature`, then `compose verify --project my-feature`.

When you ask, `compose stack --project my-feature --submit` pushes and opens one draft PR per layer.
After the PRs merge, `compose clean --project my-feature` removes what merged, moves those tasks to Done in Linear with their story and the feature, and keeps what did not merge.
A kept branch is named with its first unmatched commit.

Before the first run in a new repo, do these three things:

- Commit everything, because `run` refuses a dirty tree.
- Fill `verify.json` with the repo's lint and test commands ([verify.md](verify.md)).
- For OpenCode tasks only, add an `opencode.jsonc` allowing `edit` and `bash` so it never blocks on a prompt.

## Commands

### Projects

These commands create, list, and clean up projects.

| Command | Does |
|---|---|
| `setup` | Installs and configures everything `compose` needs ([new-machine.md](new-machine.md)). On a terminal it asks one question at a time (Quick start or Custom, a yes or no per missing step under Custom, each key with hidden input); `--yes`, or no terminal, runs the same steps with every default and never prompts. With `--dry-run` it asks the same questions and runs the same checks but changes nothing on the machine, prints each change as a `would` line, and ends with `dry run: nothing changed; N changes listed above`. It shows the Claude Code permission rules `compose` needs (`gh pr view`, `compose land`, moving a `compose/*` branch) and writes them to `~/.claude/settings.json` only on your yes; `--yes` and a dry run never write them, and rules that stay asking (`git push`, force-push, `gh pr merge`, `clean --delete-unmerged`, `clean --abandon`, `crew stop --force`) are never added. It exits 1 when Claude Code is missing. Without `--yes` it also exits 1 when a required key is missing or the model probe fails. With `--yes` it exits 0 and ends with `compose is installed but not ready:` when a required step is missing |
| `update` | Pulls the checkout with `--ff-only`, relinks the CLI, the skill, and `bp`, and runs `doctor`. It stops, naming the project, while a run or verify is live on this machine (`--force` updates anyway), and when the checkout has local changes. When the branch has commits its upstream lacks (a toolsmith's commits made in the installed copy), it rebases them onto upstream itself, dropping the ones already there; if the rebase conflicts it aborts it, lists each commit as `-` (already upstream under another hash) or `+` (only here), and prints the one command that gets it moving again: `reset --hard` when every one is `-`, else `rebase`. Commits only the checkout has stay there: put them on a branch and open a PR |
| `doctor` | Checks every setup step (the tools, links, keys by presence only, pi's provider, the herdr config, the skill files). It prints one `MISSING: <name> (install: <command>)` line per absent or too-old step and exits 1 when a required one is missing; the default-on steps print `- optional`, and the designer rows print one `designer extras not set up` line. While `claude` is missing, the steps that need it share one `waiting on Claude Code` line. It also warns about a key still in `config.json` or `.env`, and about a gh that is not logged in (`gh auth` is also a required step, so that is a `MISSING` line too). A `MISSING: Claude Code permissions: <rules> (install: compose setup) - optional` line lists the permission rules not yet in `~/.claude/settings.json`, because without them Claude Code's permission layer asks before `compose land`, `gh pr view`, and a `compose/*` branch move. It then runs the preflight that `run` and `verify` repeat at their start: a `PROBLEM: <what>; <fix>` line for an OpenRouter or Linear key its service rejects (a free key-info call, never a model call; an unreachable service is only a warning) and, with `--project`, for uncommitted changes `run` would refuse on; a `WARNING` line for a Mac on battery (closing the lid sleeps it), a 5-minute load average above twice the cores (naming the busiest process), and a docker container that keeps restarting (only when docker is installed and running). A problem exits 1 too. `COMPOSE_NO_PREFLIGHT=1` skips the key calls, the gh check, and the machine warnings (offline work). `init` runs the same check first and stops before creating anything only when a required tool is missing, and `designer` checks Framelink first and stops before printing a brief |
| `init` | Creates branch `compose/<name>` from the branch you are on, its worktree, and `.compose/<name>/`, and records that branch as `review_base`. `--here` uses this checkout, and `--after <project>` branches from another project (an existing project moves onto it while it has no commits of its own and a clean worktree, agent wiring aside, and is refused otherwise) |
| `projects` | Lists every project with done/total, last activity, title, and states, and each line ends with its `can start now:` line |
| `status` | Shows every project with every task, each with the `can start now:` line from `results/ready.json`. `--watch` redraws every 2 s, and asks git only when a result file or a branch changed. `--digest` prints one line per project instead (tasks done, failed ids, run, last verify and why it failed, a halt, questions waiting on the product owner) |
| `clean` | Drops merged layers, moves the tasks proven merged to Done in Linear and rolls their story and the feature up, refreshes the `Ready` marks, and removes a fully merged project's worktree and branch, or keeps them while the command runs inside the worktree or the team lead has not reported done (its `done` removes them). A branch is merged when it is contained in the target, when every commit has its patch there, when merging it would change nothing, or when GitHub has a merged PR for it; the review base is checked first. A kept branch is named with its first unmatched commit. `--delete-unmerged` also drops unreviewed layers. `--abandon --project <slug>` is the only way to remove an unmerged project: it lists what it removes (the worktree with its results and uncommitted changes, task, layer, and project branches, stack and test worktrees, herdr tabs) and what it keeps (Linear issues, branches pushed to a remote, PRs, the main checkout), then removes the worktree (returned to the treehouse pool when it is a slot) and the local branches. It refuses while a run is live or when run from inside the worktree, and while teammates are working unless `--force`; `--dry-run` lists and removes nothing |
| `trail` | Sets trail up again in the project's worktree |

### Tasks

These commands load the tasks, dispatch them, and steer the run.

| Command | Does |
|---|---|
| `sync` | Stores the feature and its task issues, read from Linear with the workspace's key, and refreshes the `Ready` marks; `--stdin` reads JSON from stdin instead. A task issue's `## Evidence` section is the CLI's and stays out of the task body. A task blocked by an unfinished issue outside the feature's tasks is listed with `waits on <id> (<state>)`, and `run` holds it |
| `linear <verb>` | Reads and writes Linear with the workspace's key and prints compact lines: `get <id> [--body] [--comments]` (`--body` ends with each heading's section hash), `list --parent <id>` or `--search "<terms>"` (with `--state`, `--label`), `create --title ... [--parent] [--label] [--state] [--priority] [--blocked-by]`, `update <id>` (`--title`, `--state`, `--parent`, `--label`, `--priority`, `--blocked-by`, and `--section "<heading>"`, `--append`, or `--description` for the body; `--section` replaces that section, from its heading line to the next heading of the same or a higher level, so an H2 takes its H3s and an H3 leaves its siblings, renames it when the body starts with another heading of that level, and removes it when the body is empty; `--expect <hash>`, the hash `get --body` listed, makes a `--section` write exit and write nothing when the section changed or went since that read; `--file` without a body flag, or no change at all, exits instead of printing `updated`), `comment <id>`, `labels [--create <name>]`, `project` (`--body` prints its description and section hashes; `--section`, `--append`, or `--description` write it), and `doc create --title ...`, `doc list`, `doc get <id>`, or `doc update <id>` (`--title`, and the same body flags and `--expect` as `update`; `doc get` prints section hashes too). Bodies come from `--file <path>` or stdin. `list`, `create`, and `doc list` use the project in `.compose/linear.json`, the one file in the repo's main checkout that every worktree of the repo reads; `get`, `update`, `comment`, and `doc update` refuse an issue or document in another project unless `--any-project`. `get` serves the same issue of the same Linear project read again within 30 seconds from `~/.compose/linear-get` (a stderr line says so), so a looping teammate cannot spend the workspace's shared hourly budget; `--fresh` reads Linear again, and `create`, `update`, and `comment` drop the cached reads. `--priority` is `none`, `urgent`, `high`, `medium`, or `low`, or Linear's 0-4. `--json` prints the raw fields. `LINEAR_URL` replaces the Linear GraphQL endpoint for the CLI's Linear calls (the e2e fake server uses it) |
| `tasks` | Prints the task list to review, with files, `after`, and tests. It warns on shared files |
| `route` | Routes each code task: a workflow (`test-first`, `implement-then-test`, `fix-then-regression-test`, or `check-only`) and a depth (`FAST`, `STANDARD`, or `DEEP`). Project policies with globs that match the task's files come first and raise the depth to `DEEP`; Jev answers the rest, and when it cannot, a fallback of `STANDARD` `test-first` applies. A `route:` pin in the task's compose block fixes the workflow. It prints one line per task, `<id> <depth> <workflow>  <reason>`. With a Linear key it also writes the result as the CLI's `## Route` section on the task issue and posts it as a comment. A task whose context is unchanged since its recorded route is reused (`reused`); `--recalculate` routes it again, and `--only 003,004` limits the tasks. It exits 1 when the policies cannot be read, and records nothing then |
| `quick <id>...` | Pins `route: check-only` on small work whose result shows by running it, then routes the pinned tasks. Each id is a task id, a task's or story's Linear id, or the feature's id (all its code tasks); a story names its tasks. The pin is written into the task issue's compose block on Linear and the sync cache, and a `route:` line already there is replaced. It skips, with one `<id> skipped: <why>` line each, a task that is no longer `Todo` or `Backlog` (already dispatched), one with a protected test, one that a project policy's globs apply to, and an id that names nothing (`no such task`). Pinned tasks print `<id> pinned check-only` in task id order, then go through `route` once. A check-only task gets depth `FAST` unless its route was already recorded, runs without writing a regression test, and records its red check as `skipped (check-only)`. It exits with an error and writes nothing when the workspace has no Linear key |
| `run` | Dispatches tasks. The flags are `--only 003,004`, `--attempts 3`, `--parallel N` (default `parallel` in the config, else 3), `--redo`, `--no-stack`, `--trunk <branch>`, and `--unproven`. When `verify.json` has e2e cases and the stack holds no layer yet, it first refuses unless `verify --prove` passed on exactly those cases and their `e2e_setup` and `e2e_env` (`results/prove.json`); `--unproven` runs anyway. Before anything is cloned it runs the doctor preflight and stops with every problem at once, each with its fix: uncommitted changes in the project worktree (named), an OpenRouter or Linear key its service rejects, and, unless `--no-stack`, a gh that is not logged in. A session hook's rewrite of `.claude/settings.json` or `.claude/settings.local.json` and the tools' own `graft/`, `.trail/`, `.compose/`, and `.ignore` do not count as changes. Battery, load, and crash-looping container warnings print and the run goes on. While it works, the Mac is kept awake with `caffeinate -dims -w <pid>` (macOS only, ends with the run). It records each task's red check, attempts, and outcome as evidence on the task's Linear issue ([verify.md](verify.md#evidence)); `--redo` mints a new run id per task, so earlier evidence stops counting |
| `done` | Records tasks finished by hand with `--only <ids> --note <why>` and moves them In Review on Linear. It first writes a `done` evidence event on the task's issue: while that is not saved on Linear it marks nothing done, prints `<id> not done: its done event is not saved on Linear; run compose done again`, and exits 1 after trying every id |
| `triage` | Has a fast model clean or flag each passed task (`run` ends with it) |
| `resume` | Continues a run or verify that stopped on a billing halt. `--parallel N` sets tasks at once (default `parallel` in the config, else the halted run's). It makes the same preflight and keeps the Mac awake like `run` or `verify` |
| `reflect` | Screens the settled decisions against evidence with Jev, using `--evidence -` and `--against "<line>"`. `--dismiss "<why>"` marks the evidence so far as answered, so later screens skip it |
| `hold` | Holds tasks back from dispatch with `--only <ids> --reason "<why>"`. A task the run is still preparing (clone, base, install) goes back to pending before its first turn; one already running finishes. `--release <ids>` or `all` releases them |
| `change start\|done\|undo` | Records a change of course. `undo C<n>` puts back what it touched |
| `spec-check` | Prints one `PASS|FAIL <id> <level>: <gaps>` line per issue of a feature's tree. `--stdin` reads sync JSON with no project. Exits 1 on any FAIL |
| `ready` | Labels `Ready` each story, and each feature of the epic, that is Todo or Backlog with every blocker Done or Canceled (a Design blocker counts at In Review); it writes `results/ready.json` and prints `can start now:`, and `compose linear labels --create Ready` creates the label. `sync`, the end of `run`, a `verify` PASS, and `clean` refresh the marks too |
| `bench` | Runs a frozen task set across models and reports pass rate, attempts, p50/p95 time, and cost |

### Verify and stack

These commands check the finished work and turn it into a stack.

| Command | Does |
|---|---|
| `verify` | Runs the local pipeline. `--fix 0` reports only, and `--skip-e2e` and `--skip-review` skip those stages. It first checks the keys and warns about the machine like `doctor` (a dirty tree does not stop it), and keeps the Mac awake with `caffeinate -dims -w <pid>` for the whole verify. `--prove` and every stage record evidence on Linear ([verify.md](verify.md#evidence)); while a row is unsaved it prints `verify FAIL  evidence not saved on Linear: <ids>` and exits 1 |
| `stack` | Cuts passed task branches into review layers (`review_layer_lines` in verify.json, default 300 lines, groundwork and each task's tests included), at most `max_stack_prs` layers, and registers them as one gh stack on the real base. `--submit` pushes and opens one draft PR per layer, after running verify.json `checks` (not e2e) on each layer's own tree and refusing, naming the failing layer, with nothing pushed (a layer that passed is not run again), and it stops while the base is ahead of its upstream; without it, each layer's PR title and body are printed, each marked `written` (from `.compose/<project>/pr/<name>.md`) or `generated` |
| `top` | Checks out the stack top for manual testing. `--detach` releases it |
| `reword` | Lists the stack layers' commits with the ones that break the commit rules flagged. `--set <sha>=<message>` (repeatable) rewords a commit and rebuilds the layers in the CLI's worktree, keeping each layer's branch; `--as-is` takes a message the rules refuse. The choice stays with the commit through later rebuilds. It never pushes: a layer that already has a PR gets the new commits with the next `stack --submit` |
| `land` | Merges the submitted stack bottom up with one `gh pr merge` per PR (`--method squash` by default, or `merge`, `rebase`; `land_method` in verify.json), waits up to `--timeout` minutes for each PR's required checks, then rebases the next layer onto the base, retargets its PR, and pushes it with `--force-with-lease`. It merges and pushes on GitHub, so without `--yes` it only prints the plan. A stop names the PR and a re-run resumes. Run it only when the user said to land the stack |

These commands start the teammates, collect their reports, and supervise the team lead.

| `timed <seconds> -- <command>` | Runs a command with a hard time limit, which is what teammates run tests and a project's own commands through: past the limit its whole process group is killed and the result is exit 124 with a hang hint. ## Results

Everything a run produces lands in `.compose/<project>/results/`.
Each task run writes `.compose/<project>/results/NNN.json` with every attempt's test output, timing, and cost.
Verify writes `results/verify.json`.
A run that dies shows as `interrupted` in `status`.
`resume` re-runs what did not pass and keeps passed layers.
`run`, `verify`, and `resume` work in their own session and write `results/<command>.log`.
The terminal that started one only streams that log.
Closing that terminal, or a crashed Claude session, leaves the work running.
Ctrl-C stops it.
