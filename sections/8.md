### 8. Change course
The fleet changes course when evidence shows the plan is wrong, or the product owner says it changed.
Every change of course goes through `compose change`, so it is recorded and can be undone or updated.

**What wakes you.**
- `event reflect=<file> broken=N unclear=N trigger=...`: Jev screened every live line of Decisions so far against new evidence (a task that ended without passing, a contradiction, a verify FAIL) and flagged one or more.
- `task=NNN state=contradiction`: the implementer found a fact in its brief wrong, or missing (`brief lacks <fact>`), and stopped.
- A teammate's `contradiction` report: something it found contradicts Linear.
- `event reflect=<file> error=...`: the screen could not run; judge the evidence yourself.
- The product owner's change of plans, from the engineering manager: run `compose reflect --project <slug> --evidence -` with their words to find what they touch.
- A layer you reject for a reason that may be the plan's: run `reflect --evidence -` with your reason.

**Then, in order.**
1. Hold first: `compose hold --project <slug> --rests-on <decision ids, issue ids, or reflect> --reason "<one line>"` holds every task that rests on the change, and pauses the running ones within seconds with their work kept.
   Hold before you confirm: a pause costs nothing, and a release with no change keeps all the work.
2. Steer any other teammate whose work rests on the flagged line: `herdr agent prompt <slug>-<role> "stop <that part>; keep going on the rest"`.
   The test teammates of held tasks are paused by the hold.
3. Confirm: read the reflect file, the evidence at its file:line, and the Linear line.
   Jev is a screen, never the verdict.
   Then:

| It is | Do |
|---|---|
| a false alarm | `compose reflect --project <slug> --dismiss "<why>"`, `hold --release <ids>`, a one-line comment on the task, and `run --only NNN` for a `contradiction` task |
| a brief gap (`brief lacks <fact>`, or a wrong fact the code settles) | `compose reflect --project <slug> --dismiss "<why>"`; add the fact to the brief inside `change start` / `change done`, then `run --only NNN`; never a split for a gap the brief can close |
| task-sized | `compose reflect --project <slug> --dismiss "<why>"`, then step 7 |
| objective, inside the settled decisions (a missing `after:`, a split, a wrong owner) | re-plan yourself, below, with no page |
| complex, subjective, or a reversal of anything the product owner settled | escalate, below; everything stays held |

A decision the product owner settled goes back to the product owner, even when the evidence is clear: choosing its replacement is a choice too.

**Escalate.**
1. Sync, then `compose change start --project <slug> --why "<one line>"`.
2. Start the change's architect with the reflect file, the evidence, and the held tasks: `compose architect --project <slug> --change <id> --extra - <<'EOF' | compose crew start --project <slug> --role architect --title "change <id>" --brief -`.
3. When it reports `needs-user "change <id>: <issue>: <n> questions <ids>; recommendation <one line>"`, report `needs-user "change <id> on <slug>: <what was found>. Held <ids>; the rest keeps running. <n> questions <ids>; recommendation <one line>"`, the Lavish link included when it gave one; the engineering manager asks them one at a time (0h).
4. Evidence that arrives while the change is open goes to that teammate as new open questions: `herdr agent prompt <slug>-architect "<evidence>"`.
5. When it reports `done`, re-plan.

**Re-plan.**
1. If no change is open: sync, then `compose change start --why "<one line>"`.
2. The planner teammate edits Linear: `## Plan`; it cancels the tasks that rest on the old line (a canceled task loses its `compose` block), edits the briefs that change, and adds new tasks with the next ids, and `compose testcrews --only <new and changed ids> --redo` for their tests: `--redo` rewrites the test of a passed task whose brief changed.
   You read only the tests of the new and changed tasks; a passed task whose brief and files did not change keeps its test and its acceptance verdict, and the next verify rejudges only what changed.
3. The 3b gate applies unchanged: a list that matches what the product owner just settled dispatches at once, and anything past it goes back up.
4. Settle each task `compose status` shows paused: `compose change keep|part|discard <id> [--files a,b]`; keep when its work still fits the new brief, part for the files that still do, discard when what it rested on is gone.
5. Sync, then `compose change done`: it comments the change on the feature, and refuses while a paused task is unsettled.
6. `compose hold --release <ids>`, then `compose run --only <new and redone ids> --redo` for the layers built on the old line, adding the paused tasks you kept, part kept or discarded when the run has ended (a live run restarts them on release).

**The delivery plan.**
The planner rewrites its judgment sections (Outside waits, How this maps to compose, Priority when something has to give) at each re-plan, with `compose linear doc update <id> --section "<heading>" --file <path>`.
Priority is the ranked list under Priority when something has to give; Linear's priority field stays unused.
The team lead and the engineering manager never edit the delivery plan by hand: the CLI rewrites its data sections and the planner its judgment sections.
A change to the order across features goes through the product delivery plan (sections/0p.md).

**Undo and update.**
- `compose change undo <id>` opens a new change that puts back every issue and task branch the change touched; sync, then `change done`.
  It refuses when something it touched has changed since: undo the later change first.
- An update is a new change whose reason names the change it updates: `change start --why "update C2: <why>"`.
