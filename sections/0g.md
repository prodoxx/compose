### 0g. Groundwork and the smoke check run while the product owner answers
An answer takes minutes; nothing that does not need it waits. As soon as the project exists, before or beside the first question, start one `groundwork` teammate from the CLI's template, adding only what is specific to this project (schema, stub signatures, wiring):
`compose groundwork --project <slug> --extra - <<'EOF' | compose crew start --project <slug> --role groundwork --title groundwork --brief -`
The template already carries the steps below, the e2e port rules, and phase C (the contract); never rewrite them by hand.
1. Install the repo's dependencies in the project worktree (task clones and verify borrow them).
2. Build and start the app on the current toolchain, the way a user would (`yarn build`, `go build ./...`, start the server and probe one URL), and run the existing tests; passing unit tests do not prove the app runs.
3. Write each smoke command that passed into `verify.json` `checks` (build, plus a start-and-probe one-liner when starting differs from building), so every verify re-proves it.
   `compose verify --project <slug> --skip-review --skip-e2e --fix 0` runs the checks before any task is synced, and `compose verify --project <slug> --prove` proves each e2e case fails only because the feature is missing (`run` refuses until it passes).
4. Report what is broken (a dependency that fails on current Node or Go, a toolchain bump) as decisions with a recommendation, not fixes; groundwork never changes dependencies, lockfiles, or the toolchain.
5. Once the product owner decides, the planner cuts dependency bumps, lockfile edits, and toolchain changes (`yarn upgrade`, a `resolutions` entry, `go get`) into implementer tasks like other work: the lockfile is named in `files:` and does not count toward the 350 lines; groundwork keeps writing smoke checks, stubs, and contract, and tasks implement what the product owner settled.
   A check for a tool a task sets up (a Storybook build) names the script that task adds, and that task is `kind: toolchain` (2), so its layer goes below groundwork's and every layer can run the check.
A project with Figma design work also gets the Figma plan's capability preflight (0d) before anything is planned: the designer runs `compose figma check --plan`, and a blocking limit is one question asked with the rest.
Its findings join the brainstorm (0b) as questions for the product owner; they never surface after a run as a second wave.
An autonomous mode is never a mandate to decide for the user, except away and yolo (0h), whose decisions are the recommendations, logged for the product owner's return.
A brainstorm (0b) is the exception: under away it waits for the product owner (0h).
It writes the e2e cases with the smoke checks; acceptance tests are step 3's, written in parallel from the contract it leaves.
Helpers in this phase read research, draft questions, or draw a prototype whose decision is settled; none writes a document that carries an open decision.
Research the user points at (notes, a folder of findings) feeds the feature's Notes; it is not the spec.
If a spec exists, read it and do not reopen its decisions.
Ask only about what it leaves open that the plan needs.
