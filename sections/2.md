### 2. Split into tasks
The planner teammate cuts the task issues by this step; the team lead reviews them at 3b instead of writing them.
Turn each plan step into a task issue on Linear (format below); there is no task file, the CLI reads the issue.
Tasks are tiny: one function, one component, or one resolver, which the fast model finishes in one short turn, well under a minute.
Small tasks pass first try; every miss so far was on the biggest task of its wave.
A task not obviously tiny is split; three tiny tasks finish sooner than one medium task that misses.
The split line is the reviewer's: cut where a reviewer could reject one half while approving the other, and fold setup or scaffolding into the task that needs it, never a task of its own.
The one exception is a tool verify's `checks` run (its packages, package scripts and config: a Storybook build, a new lint): its setup is a task of its own, `kind: toolchain` with no `after:`, which leads the chain so its layer goes below groundwork and every layer has the tool.
`compose spec-check` fails a check that runs a package script the base lacks unless a toolchain task owns that `package.json`, and a toolchain task with an `after:`.
A task is right-sized when all of these hold:
- one or two files in `files:` (a lockfile it names does not count), one test command, at most five acceptance criteria
- its test command runs only its own test (its file, or a name filter), never the whole suite; when another open task writes to the same test file, it filters by this task's test names (`-t`, `-k`, `-run`, `--grep`), or the other task's red cases fail its gate until they land.
  The CLI runs it after every implementer turn, so a suite there costs minutes per attempt; verify runs the full checks once, at the end.
  `compose spec-check` fails a task whose `test:` is one of verify's `checks`
- its brief (the issue description) stays under 2500 characters.
  `compose tasks` prints `WARNING TASK TOO BIG` for a task over either limit: split it before 3b, never ship it to the gate
- no open design choices; every "how" is stated or obvious from the named files
- when its test pins a line width or exact text, the brief holds that text verbatim, already wrapped line by line (a model cannot count columns)
- the whole task plus the files it touches fits comfortably in 20K tokens
- its branch will change at most 350 lines (added plus deleted).
  The CLI rejects a bigger branch, so size the task for it
- it adds no documents.
  Implementers never create .md, .txt, .rst, or docs/ files; the CLI rejects a branch that does.
  Docs are teammate work after the reviewer has merged the PRs, only when the user asked for them
- it names every file it may touch in `files:`.
  The CLI rejects a change to any other file, so a task that needs a new file lists it.
  A file the task removes goes under `delete:`, never `files:`: an implementer cannot delete a file, and `run` removes the `delete:` paths itself (docs/tasks.md)
  Two tasks never share a file; a shared file means they are one task or one is `after:` the other
- it is independent of other pending tasks, or its `after:` names the task whose code it needs.
  An `after:` task branches from that task's tip, so its code is there
Dependencies are only for code a task needs: it calls a function, imports a type, or edits a file that another task creates or owns.
Never add `after:` for reading order, story order, or "the server before the client": every `after:` makes a task wait, and unrelated tasks must run in parallel.
Review order comes from ids: the stack puts a task above its `after:` tasks and orders the rest by id, so an `after:` is never needed to set it.
A pure function, a component, and a store method usually depend on nothing.
`compose tasks` and `spec-check` flag a task whose brief or test command names a file another task owns when it has no `after:` path to that task, and give the `after:` to add; drop the file from the brief when the task does not need that code.
A Python brief that names only code already on the base (`fc_tasks.load_tasks`, `from fc_tasks import load_tasks`) needs no `after:`: any name the base lacks, the path itself, or a bare `import fc_tasks` still does.
`compose tasks` prints the run waves and a `WARNING SERIAL CHAIN`, and exits 1, when most tasks wait on one another; cut every edge that is not a real code need before 3b.
If its test cannot be written, it is not a task yet.
Split further, or brief a teammate session for it whole.
A task is a **task issue** on Linear: a sub-issue of its story, labelled `Task`, state Todo, its title the task's title, its description the brief (Goal, Acceptance criteria, Test plan, Constraints, and Interfaces when something crosses the task's boundary) ending with the `compose` block, and `blockedBy` set to the issue of each task it builds on.
That one issue is the CLI's contract, the implementer's brief, and where humans watch and edit the work.
The CLI reads Linear only when you ask it to. **Sync** right before every `tasks`, `run`, `resume`, and `verify`, so an edit anyone made in Linear is what runs.
Run `compose sync --repo <wt> --project <slug>`: it reads the feature, its stories, and their tasks from Linear with the workspace's key (read-only, descriptions whole) and hands each description to the implementer as the brief.
`--stdin` reads the same JSON from stdin instead, for scripts and tests.
The commands refuse to start without a sync, and `sync` refuses a feature other than `linear.json`'s.
One feature, one stack.
The project's tasks become the layers of a single `gh stack` on the branch the user invoked you from, in `after:` order and then id order: foundational code at the bottom, code that depends on it above, one concern per layer.
Number tasks in the order a reviewer should read them.
A new task's id comes from `compose linear next-task-id --project <slug>`: it reads the compose block of every issue in the Linear project, so a task of a story outside `linear.json`'s `stories` still counts, and an id is never reused.
Independent tasks still run in parallel from trunk; the CLI rebases them into the one chain only when it registers the stack after the run.
