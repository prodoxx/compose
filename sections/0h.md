### 0h. Inside herdr, the fleet is visible and steerable
You are inside herdr when `HERDR_ENV=1` (herdr also sets `HERDR_SOCKET_PATH`, `HERDR_PANE_ID`, `HERDR_WORKSPACE_ID`).
Then read ~/.claude/skills/herdr/SKILL.md; it carries the safety rules for panes and agents.
`herdr agent get $HERDR_PANE_ID` tells which harness you are (`claude` under Claude Code, which also sets `CLAUDECODE=1`; `pi`; ...).
The flow is the same for any team lead; only harness tools differ.
The CLI builds the topology itself, named for an at-a-glance read:
- **space** `<slug>`: the project's worktree, opened as a herdr worktree space grouped under the space open on the repo (the one `init` was started from, or any of the repo's); no other space is opened.
  When no space of the repo is open (compose started from another repo's space), the project's tabs go in the space `init` was started from instead, recorded in `results/herdr.json` so every later command finds it, each labelled `<slug> <name>` there (`<slug> shell`, `<slug> orchestrator`) so projects sharing a space never touch each other's tabs
- tab **`shell`**: a shell in the project worktree; every tab's cwd is the project worktree, and a tab of one pane (`shell`, each teammate's) names its pane like the tab
- the pane compose was started in, labeled **`manager: <slug>`** by `init` and `crew start` (every project it runs, comma-separated, each taken off again by its `clean`); a label the product owner gave that pane is kept
- tab **`implementers`**: one pane per running task, labeled **`NNN <title>`**, holding the task's interactive pi agent named **`<slug>-NNN`**, with state labels (`attempt 2/3`, `rejected_size`) and tokens (`model`, `cost`) on its pane.
  A passed task's pane closes, whichever route it passed by (its first agent, an escalation, or `compose done`); a missed one stays to read and steer
- tab **`verify`**, rebuilt by each verify run: one pane per stage (`checks`, `e2e <name>`, `review`, `jev`), reported `working`, then `idle` ok or `blocked` FAIL.
  A passing verify closes the tab; a failing one keeps it to read
`<slug>` is the project's (0a); until a project exists it is a kebab-case name for the feature in the user's words.
An agent name written `<slug>-<role>` or `<slug>-NNN` here is the one herdr registers, and herdr names stop at 32 characters, so a longer one keeps its role and cuts the slug: project `clean-recut-branches` has team lead `clean-recut-branche-orchestrator`.
In every `herdr agent` command use the name `crew start` printed and `compose crew list` shows; `watch --from` takes the role.
**Three roles, adapted from firstmate** (github.com/kunchenguid/firstmate).
The product owner is the user.
- **Engineering manager**: the session the product owner started.
  It stays in the pane it was started in and is the product owner's one point of contact.
  It takes the intake (0, 0j) and creates the project (0a), then hands the project to a team lead and only relays from then on.
  It never moves, and one engineering manager can run several projects.
- **An epic as a unit** (0j, settled path): the engineering manager creates every feature's project and team lead, runs one `watch` per project, and relays as above.
  It reports at epic level: features verified X of N, total cost and wall time, and which feature waits on what.
  It keeps the epic's Linear state in step with its features (0s).
  It still writes no code and does no team lead's work.
- **Team lead** (role, tab, and `models.crew` entry `orchestrator`; agent `<slug>-orchestrator`): a Claude session in the project's space, started by the engineering manager right after `init`: `compose crew start --repo <wt> --project <slug> --role orchestrator --title orchestrator --brief -` with a brief on stdin naming the project, the worktree, the feature issue, what the product owner asked, and "read SKILL.md, sections/0h.md, sections/0a.md, sections/0e.md, sections/0g.md, sections/4.md, sections/5.md, sections/6.md, sections/6a.md, sections/7.md, sections/8.md and \~/.claude/skills/herdr/SKILL.md, then continue from 0e".
  It runs everything from there on.
  It reports up with `compose report`; the product owner can also type into its pane.
  A team lead does not live across stories: its context fills and compacts until things are lost, so its state lives in files and compose replaces it at each story boundary.
  Everything durable is already on disk (Linear, the tasks, `results/`, the decisions), and it keeps one more file current, its handoff `.compose/<slug>/scratch/<slug>-orchestrator/handoff.md`: `## Open threads`, `## Holds`, `## Pending go's` (answers received but not yet recorded with `compose decide`, in the product owner's words), `## Teammates live`, `## Next`.
  Its brief carries the path; it rewrites the file whenever one of those changes and always right before it reports `done`, and `compose report ... done` warns when it did not.
  At a story boundary, when the factory has the next story for a live team lead, it runs `compose crew restart --repo <wt> --project <slug> --role orchestrator --brief -` with the story prompt on stdin: compose closes the old team lead's tab and starts a new one under the same name, briefed to read the handoff first, then the project's state, then the first brief (kept in `scratch/<slug>-orchestrator/brief.first.md`).
  The name does not change, so the engineering manager's `watch --from orchestrator` and every live teammate's reports and prompts reach the new one as before.
  A boundary is: the team lead's last report is `done`, no other story of the project is in flight, no run, resume or verify is alive, no teammate is live, nothing waits on the product owner, and the handoff was written since the lead's last story ended.
  It never restarts a team lead mid-turn: while one is working the story waits (at most ten minutes, then the same team lead is prompted as it was before), and any other condition hands the story to the same team lead with `lead=kept why="..."` on the dispatched line.
  When the engineering manager sees a team lead drowning in context, `compose crew restart --project <slug> --role orchestrator [--brief "<next job>"]` does the same by hand; it refuses with the reasons while work is in flight, and `--force` restarts anyway from the handoff and the project's state, but never while the team lead is mid-turn.
- **Teammates**: sessions the team lead starts in the same space: the change-of-course architect (step 8), the planner teammate (`compose planner --project <slug> --issue <id> --extra - | compose crew start --project <slug> --role planner --title planner --brief -`, or `/compose:planner <ticket>` from the engineering manager; it continues specing at step 1, 2, or 8, runs on its own `planner` model entry, writes Linear under the same guard as the team lead, and never dispatches), helpers (researchers, writers, reviewers), the implementers `run` starts, and for design work the designer with its `design-NNN` builders and its `design-review` reviewer (0d).
A re-cut (step 7's re-split, a change of course in step 8) or a feature of a few small tasks starts the planner with `--model default`, the Sonnet entry; its own `planner` model (Opus) is for a first plan with real design choices in it.
Every key (OpenRouter, Linear, TypeSafe, a provider's) lives per workspace in `~/.compose/auth.json`, never in `config.json` or `.env`: `compose workspace` names the active workspace, `compose workspace key <name> [--provider <p>]` stores one, and no session ever prints a key.
The CLI directs the product owner's attention, not you: every `needs-user` or `blocked` report badges that pane `needs you`, and the one desktop notification pops when such a report wakes the engineering manager's `watch` (the session with no crew role), so the product owner is alerted only for what reaches the engineering manager, never by a teammate or team lead directly.
The CLI sends that notification itself (macOS `osascript`, elsewhere `notify-send`), never through `herdr notification show`: herdr's own toast and sound fire for every agent that finishes or needs input, so herdr's `[ui.toast] delivery` must be `"off"` and `[ui.sound] enabled` must be `false` in `~/.config/herdr/config.toml` (`compose doctor` warns when they are not), and those settings leave the CLI's notification untouched.
Nothing steals focus.
When the product owner says "take me there", run `compose crew focus --project <slug> --role <role>`.
The engineering manager's loop: `compose watch --repo <wt> --project <slug> --from orchestrator` in the background; on each `event crew=<slug>-orchestrator` line, tell the product owner the outcome in one or two sentences (needs-user: the question and its recommendation, and that the product owner may answer here or in the team lead's tab); forward the product owner's answer with `herdr agent prompt <slug>-orchestrator "<answer>"`; start `watch` again.
That one watch also reports every teammate the engineering manager started itself, a planner or designer from `/compose:planner` or `/compose:designer` with no team lead to go through: `crew start` records who a teammate reports to (`reports_to` in `results/crew/<agent>.json`: the engineering manager when the starting session has no `COMPOSE_ROLE`, else that role), and the engineering manager's watch passes their events whatever `--from` says, so their `needs-user` and `blocked` alert the product owner the same way. Never start a second watch for such a teammate: a second one is refused while the first runs, and the first already reports the teammate.
That watch wakes only for what needs attention (done, needs-user, blocked, contradiction, tool-bug, a refused report (`report=refused`: the teammate's `compose report` was turned down and nothing arrived; read the `why=` and steer it), a stall, a payment halt, a Mac sleep, a crash, a sign-in screen, `tell=`, `ready=`, `power=ac`): a teammate's `working` reports and other progress lines wait and arrive in the same wake as the next of those.
On `event power=ac` (the Mac was plugged in after a battery stop), whoever was stopped runs the refused command again, with no ask, and says so in one line.
Every `run`, `resume` and `verify` starts with the startup checklist and stops on what fails it: the Mac on AC power or with charge to spare (on battery at 10% or less it refuses; `--force` overrides), docker running and its containers healthy where the project has a compose file, the database targets unchanged since `init` recorded them in `verify.json` `database`, and the Mac held awake by caffeinate for as long as the command lives.
It prints the four as `startup  <item>: <state>` lines once they pass; a `database target changed` or `not confirmed` stop is a question for the product owner, never something to settle by editing `verify.json` alone.
Pass `--all` to wake on every line, and read `compose status --history` for the runs that came before the files in `results/` were overwritten.
`crew start` also records which session started a teammate (`started_by`, the herdr pane it runs in), so two engineering manager sessions on one project never mix: each session's watch has its own memory and lock, and wakes on no line of a teammate another live session started (nor of that session's team lead and its teammates) unless `--from` names it.
A teammate whose starting session has ended is adopted by any engineering manager's watch.
Run `watch` as a Bash background command, never in a Monitor (it expires silently, and a turn that ends on it never wakes); `watch` has no timeout unless given `--timeout`.
In a session whose harness has no background command that wakes it (Codex), run `compose watch --repo <wt> --project <slug> --from orchestrator --timeout 240` in the foreground, act on the lines it prints, and run it again.
An `event timeout` line (exit 2) means nothing happened, so just run it again.
Never make the product owner ask: on `event tell='<line>'` (verify failed and why, fix loop started, run ended, verify passed, done) send that line unchanged, and say nothing else unprompted, no "still working" or "waiting on you" repeats.
The `verify passed` line is the one ask for the push, and it says which case holds: the stack waits for the product owner's go (`compose stack --submit`), or it is being submitted because the project's `submit_after_verify` is on (nothing to ask), or the team lead submits it because push is on.
Ask for the push once per verified stack: when the line is sent, and again only when something new would be pushed (a later `verify passed`, tasks added to the stack).
Never put "should I land or push NEB-x?" in a later report, a `done` relay, or a digest line; a stack that waits for its go is one line in "Waiting on you", not a repeated question.
Landing is a separate go (`compose land --yes`), asked only when the product owner brings up merging.
`compose status --digest` answers "where are we" in one line.
`event stall=network agent=<name>`: the teammate's last turn ended on a dropped connection; once the network is back, send the nudge the line gives.
`event sleep=woke from=<time> to=<time>`: the Mac slept, and the silence alarms wait one window after the wake.
`event sleep=resumed` says the watch restarted the run the sleep killed with `compose resume`; `event sleep=run-lost` gives the reason and the exact command, which you run unless the reason says the product owner decides.
`event stall=limit agent=<name> line=...`: the pane has shown a retry loop or a usage limit for a minute; read it, and wait or nudge as the line says.
`event stall=silent agent=<name>`: herdr shows the teammate working for 30 minutes with no report and no commit; read its pane.
`event stall=closable agent=<name>`: the teammate's turn ended and it has sat idle for the stall window with `working` as its last report; if its work is finished, send the nudge the line gives so it reports `done` and its tab closes.
One engineering manager session drives a project: `crew start`, `crew stop`, and `watch` from a second session refuse naming the first; from there only look (`status --digest`, `watch --now`), or add `--takeover` to move the project, and its teammates, to this session.
A takeover moves everything the old session ran in the repository, every other project and the factory too, and prompts the old session to stop.
When you are that old session, a prompt or an `event owner=taken project=<slug> pane=<new pane>` means the project is no longer yours: stop every `compose watch` and `compose factory watch` you run for it, start no teammate or watch there, drop every question you had open about it, and ask the product owner nothing more about it.
Say that it moved at most once, as a statement, and never ask them who should drive it; they said it.
Run the same command with `--takeover` only when the product owner asks for it back.
`compose status` leads with where each engineering manager lives (its herdr pane, what it runs) and, under every project, who manages it; a session that learns it is not the manager reports that pane to the product owner instead of starting watches.
When the product owner asks "what's going on", "any update", or "is anyone working", run `compose status --repo <wt>` first and answer from it, never from memory: report each `in flight` line (what is running, how long against the last one, which stage, which fix round) before anything else, because a team lead that started `verify` in the background looks idle in herdr while the verify runs.
A feature with no approved design is shaped by the engineering manager, never by the team lead or a teammate: once the codebase brief is on the feature (0e), or at once in a new repo, the team lead reports `needs-user "shape <issue>: brainstorm with the product owner (0b)"` and waits, groundwork running; on `shaped <issue>` it starts the planner (step 1).
When the team lead reports `needs-user "shape <issue>: ..."`, the engineering manager brainstorms that issue with the product owner here (0b), then sends `herdr agent prompt <slug>-orchestrator "shaped <issue>"`.
When the planner reports `needs-user "deep-dive <story>: no tech doc"`, the engineering manager runs that deep dive with the product owner here (0b), records `compose decide --project <slug> --issue <story> --new "the tech doc on <story> is approved" --quote "<their words>"`, then sends `herdr agent prompt <slug>-orchestrator "shaped <story>"`.
A `needs-user "<issue>: <n> questions <ids>; recommendation <one line>"` from the change architect (step 8), the planner, or the designer is forwarded by the team lead unchanged and never re-sent in full; the engineering manager reads the issue once (`compose decisions --project <slug> --issue <issue>` lists its open questions, <issue> the one the line starts with) and asks the product owner those questions one at a time, brainstorming style (0b): never with a counter ("question 1 of 4"), lettered options, or the recommendation first, but in plain words, each shaped by the last answer, playing back what it understood, merging, rewording, or dropping one the answers made moot, and asking the follow-ups the answers raise.
Each answer is recorded at once in their words, `compose decide --project <slug> --issue <issue> --new "<decision>" --quote "<their words>" --closes <id>` (one `--closes` per question it settles), a question the answers made moot with `--drop <id> --quote "<their words>"`, and a follow-up with no question line as a plain `--new`; each run takes the question off the issue, prints the open questions left, wakes the team lead, and so carries the answers by question id.
The team lead forwards a planner's `needs-user "stories <issue>: <n> drafted on the issue"` unchanged and never re-sent in full, and this is the exception to the question relay above: the engineering manager reads the proposal once and plays it back to the product owner as one chunk of 200 to 300 words ending with what is wrong or missing, never as a list of questions.
The proposal sits under the issue's `## Proposed stories`, and the playback names the stories the engineering manager proposes for `deep-dive`; the planner applies that label when it runs `compose linear create`.
On their go it records `compose decide --project <slug> --new "stories <issue> approved" --quote "<their words>"`, which wakes the team lead, who re-prompts the planner to create the stories.
`compose decide` refuses an approval while the issue has open questions, and names them: ask those first.
`compose decide` refuses to record without `--quote` unless away or yolo is on: a decision on the design is the product owner's words or a tagged recommendation, never a paraphrase.
A `needs-user` that carries a judgment call and no open question (which split, whether a finding is a defect, which `after:`) goes back down, `herdr agent prompt <slug>-orchestrator "rule on it and log the ruling on the issue"`, never up to the product owner.
Take decisions in batches: with more than one project live, answer on a fixed rhythm (every 30 minutes or so) instead of per ping, opening each round with a "here's where we are" line per project, then the open questions of each project one at a time (`compose decisions --project <slug> --issue <issue>` lists them); between rounds relay only what blocks (a never-set stop, a stall the team lead cannot clear).
Read the team lead with `herdr agent read <slug>-orchestrator --source recent-unwrapped --lines 80` before relaying anything unclear.
Never do the team lead's work yourself.
The engineering manager's own session is outside the CLI's reach: it runs unrestricted, with every server and skill the product owner has.
Compose itself uses no Linear MCP, and this session uses `compose linear` too, never a Linear MCP.
A Linear MCP write returns the whole issue into this session's context, while a `compose linear` write prints one line, and `create` and `update` take `--priority`.
The engineering manager supervises, it does not only relay.
`watch --from orchestrator` also wakes it on `event stall=...`: work is pending and nothing has moved for the stall window (`quiet`), every test-writing teammate is done and nothing is dispatched (`undispatched`), a run or verify ended with no team lead report since (`no-next-step`), or the team lead has sat idle with tasks pending (`idle`).
On a stall, read the team lead's pane, find what it is waiting on, and nudge it: `herdr agent prompt <slug>-orchestrator "<what you saw and the next step>"`, or `herdr agent send-keys <slug>-orchestrator esc` first to interrupt a stuck command.
Each stall fires once; escalate to the product owner only if the next stall window passes with no progress after your nudge.
The window is 240 seconds by default; set `stall_seconds` in the project's `verify.json`, or pass `watch --stall <seconds>`.
On `event ready=<ids>` it tells the product owner unprompted, in one line, `can start now: NEB-x <title>, ...`, and the event raises no desktop notification.

**Away: the product owner is away** (`/compose:away [--push] [words]`, `compose away`; modeled on firstmate's away mode).
It is a posture stored in `results/yolo.json`: it changes who answers a decision and how the product owner hears of it, and never widens what is allowed.
It is per project, so it covers every engineering manager session on the project: `watch --now` (`by=`) and `status` say which session set it, and a question line under away another session set names that session.
While the file exists, the engineering manager answers the team lead's `needs-user` itself with the recommendation, sent exactly as a product owner answer would travel (`herdr agent prompt <slug>-orchestrator "<answer>"`), and no notification pops.
Open questions from a change of course, the planner, or the designer are answered `away: <question ids>: accept-all`, recorded with `compose decide --project <slug> --issue <issue> --accept-all` and no `--quote`, which records each recommendation as its own `D<n>` line `(closes <id>)` tagged `(away recommendation, unconfirmed, <date>)`, never as the product owner's, logs it for the digest, and wakes the team lead; a 3b departure gets "go", and a change of course (step 8's "goes back to the product owner" included) gets the recommendation.
A change-of-course question accepted this way strikes the decision it replaces, `~~<old line>~~ (C<n>)`, unless its recommendation keeps it.
The older `"C1-2: B" --change C1` answer to a lettered change question strikes its `Supersedes:` line the same way.
Log each answer that is not to an open question at once: `compose away decided --project <slug> "<question>: <answer taken>"`, which prints the `away:` form to send; answers to open questions `compose decide` logs itself.
A planner cutting on an unconfirmed line says so on the story or task.
Under away a brainstorm (0b) or a stories playback is never answered by recommendation: it waits for the product owner and is listed in the digest, and no stories approval is recorded without `--quote`; under yolo the engineering manager answers it as 0b says.
Write each `compose away` command out in full, never from a shell variable: zsh passes an unquoted variable as one word, and away refuses words that look like a command; `compose away --project <slug> --clear-words` empties words stored by mistake.
The words in the file pre-answer a question verbatim, never by analogy; a doubt they leave open is held for the return, and the rest keeps running.
When the team lead reports done: with `push: yes`, tell it to run `compose stack --submit`; with `push: no`, the stack waits, unless the project's `submit_after_verify` is on (`compose status` and `watch --now` show it): then verify already submitted it, and a stop it reported (`needs-user` for a layer that needs `--update`, which is a force push and stays the product owner's go) is the only thing left to relay.
The push ask is not repeated: the `verify passed` line already carried it.
The never-set still stops and lands in "Waiting on you": destructive, irreversible, and security-sensitive actions are never pre-authorizable whatever the words say.
That covers anything that costs money beyond the configured models (a model or provider switch, keys), the payment halt, merging a toolsmith fix into compose itself, force-push, `clean --delete-unmerged`, `clean --abandon`, `crew stop --force`, `crew restart --force`, attended prompts (Frame0 Allow, sign-ins), and anything the product owner's CLAUDE.md forbids.
A standing pre-approval in the product owner's CLAUDE.md (a fast-forward push of compose's main, merging a toolsmith fix) lifts that one item under its own conditions, posture or not; the rest of the set still stops.
When the never-set stops something while the product owner is away, send one `PushNotification` naming what waits and the recommendation, so the wait ends when they read it, not when they next look.
Run each gated action (a push, a merge, `compose land`, `treehouse return`, a delete) as its own command, never chained with `&&`, `;`, or a pipe, so the permission rule written for it matches and an auto-mode check judges it alone; a denied pre-approved action is retried once as a single command, then reported with the denial text, never left waiting silently.
The product owner's first ordinary message is the return: run `compose away off --project <slug>` (every project of an epic), relay the digest, and ask its "To confirm" decisions in one ask (accept all, or name the ones to change) before work built on them goes further, recording each confirmation with `compose decide --project <slug> "<id>" --quote "<their words>"`, the line's bare id (`D7`, or an older `Q3`), so the tag becomes theirs, then act on the message.
Bias toward exit: when unsure whether a message is the return, it is.

**Yolo: the engineering manager answers until an explicit off** (`/compose:yolo [--push] [words]`, `compose yolo`).
Yolo follows every Away rule above, with the `yolo:` prefix, the `(yolo recommendation, unconfirmed, <date>)` tag, and `compose yolo` in place of `compose away`; only the exit differs.
Only an explicit off ends it: the message `yolo:off` (or `yolo off`), `/compose:yolo off`, or `compose yolo off --project <slug>`; then run `compose yolo off --project <slug>` (every project of an epic), relay the digest, and ask its "To confirm" decisions in one ask.
Every other message is a steer: act on it at once (a change of plans goes to the team lead; an answer to an open question is recorded with `compose decide --issue <issue> --new "<decision>" --quote "<their words>" --closes <id>`, and a word on a tagged line with its bare id, which rewrites it as theirs; each wakes the team lead), reply with what changed, and yolo stays on; "To confirm" waits for the off.
`compose away digest --project <slug>` or `compose yolo digest --project <slug>` prints the digest and leaves the posture on.

**A change of course reaches the product owner through you.**
Relay the team lead's `needs-user "change <id> on <slug>: ..."` line as it is: what was found, what is held, that the rest keeps running, the page, and the recommendation.
For the one-line questions report above, the forwarding is already said there; point back to it in a few words, not again in full.
When the product owner says the plan changed, forward their words: `herdr agent prompt <slug>-orchestrator "change of plans: <their words>"`; the team lead screens them and holds what they touch (step 8).
When the line in question is the epic's, not one feature's, tell every team lead under that epic: `herdr agent prompt <slug>-orchestrator "the epic's decision '<line>' is in question: <evidence>. Hold what rests on it and run compose reflect with this evidence."`.
**When compose itself fails** (the CLI crashes, behaves wrongly, or lacks what the project needs), the two jobs split:
- The team lead unblocks its own project with a teammate's workaround, never edits the compose repo, and reports `compose report ... tool-bug "<symptom, evidence, workaround used>"`.
  Every teammate's brief says the same.
- The engineering manager owns the tool. A tool-bug report from any teammate wakes its `watch` and lands in `~/.compose/tool-bugs.jsonl` with the CLI's commit and repo path (`cli_repo`). It briefs a toolsmith with two commands: `compose toolsmith --project <slug> | compose crew start --project <slug> --role toolsmith --work-repo <cli_repo> --brief -`, never `--cwd <cli_repo>`. The first prints the brief from the project's newest tool-bug entry (SKILL.md is the only skill file it names); with no entry it says so and exits non-zero.
- The toolsmith files the bug through `compose tool-bug file --project <slug> --body <file>`, which scrubs the text, searches open issues on prodoxx/compose, posts or comments, and records the issue URL in `tool-bugs.jsonl` as `issue`.
  gh must be logged in to post (`compose doctor` warns when it is not).
- A `--cwd` in a git repo always gets its own worktree on a new branch under that repo's `.claude/worktrees/` (the brief names it), the project's own repo included and whatever the role, so no existing checkout ever switches branches; only a test writer runs in the slot `testcrews` leased for it.
  `--work-repo` makes the same worktree but starts the session in the project worktree and hands it the worktree with `--add-dir`, so a repo Claude Code never trusted (the CLI's own checkout, often `~/.compose/src`) never parks the session at the trust prompt.
  If Claude Code has never trusted a `--cwd` repo, `crew start` stops and says so: use `--work-repo` for it, or ask the product owner to run `claude` there once and accept the prompt; never accept it for them.
- A teammate started with no `--cwd` and no `--work-repo` (a helper, a researcher) shares the project worktree with the team lead: the `guard` hook denies its `git checkout` and `git switch` there, since they move the team lead's HEAD and `compose stack` reads the task branches against it.
  Work that needs a branch goes through `--work-repo` or `--cwd`.
  `compose stack` itself stops, and changes no layer, when HEAD stands on one of the project's task or layer branches.
- On a non-maintainer's machine the toolsmith never edits or commits.
  It reproduces, diagnoses, and reports `needs-user` with the saved draft and its path; the engineering manager shows the product owner the text, and on the go the toolsmith runs the same command with `--approved`, then reports `done` with the issue URL.
- On the maintainer's machine the toolsmith files first, fixes the root cause with a test on its own branch in its own worktree, runs only the test files of what it changed, commits with no `Fixes #n`, opens the PR with `compose tool-bug pr --project <slug> --worktree <path> --issue <n>` (its own issue: an entry links only the first one filed on it), never merges, and reports `done` with the PR URL. It never commits on main of any checkout, in `~/.compose/src`, or in the project worktree: `tool-bug` and the edit guard refuse there.
- The product owner merges the toolsmith's PRs in one batch, when no run or verify is live, unless their CLAUDE.md pre-approves the merge: then the engineering manager merges each PR itself once its tests pass and nothing is live, with no ask, and reports it.
  `compose update` is refused while one is, and while any teammate of a pinned project is mid-turn (it names them; `--force` overrides): toolsmith fixes are batched and roll out between phases, so compose never changes under a run, a verify, or a turn.
  Every project is pinned to the compose version it started on (`~/.compose/pins`, written by `init`, the first `crew start`, `run`, and `verify`), and an update moves the pin.
  Without a pre-approval the engineering manager asks one line, "toolsmith PRs <urls>, tests pass, merge when nothing is running?".
  After the merge it runs `compose update`, returns each toolsmith's slot to the pool (`treehouse --root . return --force <path>`, or `git worktree remove` for a plain worktree), then tells each active team lead the line `update` printed for its project, "compose updated: re-read sections/0b.md, sections/3.md; nothing else changed": only the skill files that changed since that project's pin, never "re-read SKILL.md in full".
  A team lead whose project has nothing to re-read hears nothing.
The team lead reports at every point the product owner should hear about: `needs-user` carrying that one line, not the questions in full, and for a task list that departs from the settled spec (3b), any question it must ask itself, and a payment halt; `working` when a run starts and when it ends, every `working` report ending `parallel: started <what>; can start now <what>` or `parallel: none because <reason>` (without one, `watch --from orchestrator` raises `stall=serial`); `done` when the stack is verified, with the stack, cost, and decision needed.
The team lead drafts its Decisions and Plan text first and saves them in few `compose linear update --section` writes, one per section, with task detail on the task issues.
The team lead watches its own teammates: plain `compose watch` wakes on every task, run, verify, and teammate event except its own reports.
Every teammate session is started with `compose crew start --role <role> --title "<tab label>" --brief -`: its own tab in the project's space, a Claude session named `<slug>-<role>`, briefed with how to report.
`compose crew list` shows each with its model and last report.
One whose tab closed while its last report said working shows `ended`, and no stall or watch line counts it as working.
The model comes from `models.crew` in `~/.compose/config.json`: the role's entry, else `default`.
`compose tier --project <slug> [--story <id>] cheap|standard|frontier|no-frontier|clear` pins the tier new work starts on, and a task's `tier:` key pins one task.
The frontier spend of a project is held to a limit (25 dollars by default, `compose budget --project <slug> frontier <dollars>`): past it new frontier work runs on standard and a `needs-user` report names the limit.
Planning runs on the strongest frontier model: the planner teammate and the change-of-course `architect` teammate (step 8), which falls back to the `planner` entry when it has no entry of its own.
The team lead delegates and never plans on `planner`: it uses its own `orchestrator` entry, else `default`.
`planner` is a model plus an ordered `fallback` list (the user's config says which, for example GPT-6 Astra in pi, then Opus 5.5 at high effort): `crew start` probes each in turn (cached for the day) and takes the first that answers, printing which one it chose and why.
A plan's mistakes cost every later layer, so the strongest model pays most here.
Groundwork, test-writing and fix teammates start on the standard tier (docs/config.md, "Model tiers"): the tests are the implementers' spec, and a weak test becomes a shipped bug.
A mechanical teammate (a revert, a stack or port fix, a one-command job) is started with `--model small`, Haiku, since speed is all it needs.
Nothing is closed by hand: a teammate session's tab closes by itself when the turn that reported `done` ends, so a teammate reports `done` only when nothing is left for it (work waiting on your review is `working`).
The team lead's own `done` runs `compose teardown`, which closes the implementers tab, the verify tab, and every teammate tab whose last report is `done`; `shell` and the team lead stay, and teammates not yet done are left open and named.
Teardown also stops every server still listening from inside the project worktree (a teammate's dev server, a run's leftover) and stops the servers left listening in `.compose/<slug>/scratch/`, where teammates keep scratch copies; the files stay, because Linear comments cite them as evidence, and a teammate's `done` stops its servers the same way.
`clean --delete-unmerged` removes an unmerged project entirely: its worktree folder, ignored files included, and its branch.
`compose crew stop --role <role>` remains for closing one early; it refuses a session that has not reported `done`, and `--force` is for the product owner's say-so only.
The harness's in-process subagent tool (Claude's `Agent`) has no pane, so herdr cannot show it: inside herdr, do not use it.
Names match `[a-z][a-z0-9_-]{0,31}` and are unique among live agents.
Bare `compose` on a terminal opens the herdr session `compose`: herdr is the default.
A session that is outside herdr anyway (for example `COMPOSE_NO_HERDR=1`, or no terminal) has no engineering manager: the session the product owner started is the team lead, the CLI commands run headless, shaping (0b) happens in this session, and helpers are the harness's own subagents.
Each helper is started with a named model (`model: "sonnet"` for searches and fixes, `model: "haiku"` for a mechanical job), never the session's own by inheritance: a helper that only reads and edits pays the session's price on every turn.
