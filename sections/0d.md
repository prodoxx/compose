### 0d. Design work: the designer
The designer continues design work in Figma from where it stopped.
It enters this workflow at the design step; it is no new workflow.
Start it with `/compose:designer <ticket> [--figma <file url or key>]`, or by hand:
`compose designer --project <slug> | compose crew start --project <slug> --role designer --title designer --brief -`.
The designer starts Frame0 only to see or draw wireframes: `compose frame0 up --project <slug>` right before the first export or drawing, never at its start, and `compose frame0 down --project <slug>` when it is done with them; no session has `frame0` tools.
Its builders and reviewer never touch Frame0.
A session changes Frame0 only through `compose frame0` commands (`up`, `draw`, `export`, `pages`, `move`, `delete`, `links`, `lint`, `down`), never `curl` on its API or token.
The owner of the ticket's level starts it: for a feature or story whose project has a live team lead (`compose crew list --project <slug>` shows `<slug>-orchestrator`), the engineering manager hands the start to it with `herdr agent prompt <slug>-orchestrator "start the designer for <ticket>: <that pipeline>"`; for an epic, or with no live team lead, the engineering manager runs the pipeline itself.
The starter only relays from then on, as the engineering manager does for a team lead: `compose watch --project <slug> --from designer` (the engineering manager watches `--from orchestrator` when the team lead started it), and answers forwarded with `herdr agent prompt <slug>-designer "<answer>"`.
The starter passes `event ready=<ids>` on to the product owner the same way, unprompted, in one line, `can start now: NEB-x <title>, ...`; the event raises no desktop notification.
It is never inline: the designer works in its own pane and starts its crew in theirs.
`compose figma check --project <slug> --figma <file url or key>` stores the target file's key in `.compose/<slug>/linear.json`; with no key stored, the designer asks the product owner for the file.
Figma serves `use_figma` only to allowlisted clients, so the designer and its whole crew are Claude sessions.
Before any build, the groundwork teammate runs `compose figma check --project <slug>` to prove Framelink reads the file.
The write connector is proved by the designer's first write, the capability probe below.
Before any planning, the designer runs the capability preflight (its brief, step 3): one `use_figma` write probe on the stored file measures its pages and modes, and its result goes to `compose figma check --project <slug> --pages <pages> --modes <modes> [--need-pages N] [--need-modes N]`, which stores the plan's limits (pages per file, modes per collection, library publish, Code Connect) and the tier they show as `figma_caps` in `linear.json`; the brief prints them.
The probe states only what it proved: a tier shows only when a mode limit was hit, and otherwise the tier, Code Connect and library publish are `unknown`, as is a page limit on a file that already has 6 pages.
By default the design system needs 2 modes (Light and Dark), so a Starter plan (1 mode, 3 pages) blocks it.
A recorded decision on modes wins over that default, and a single mode is allowed: when the Decisions so far say light only, the designer passes `--need-modes 1`, plans the foundations in one mode, and a Starter plan does not block it.
No Figma tool reports the plan, and Figma's REST API does not either, so the probe is the only source; `--plan <tier>` is for a tier the product owner names, and its limits are predicted until a probe replaces them.
A limit that still blocks is one up-front `needs-user` question, upgrade or design around it, raised before planning; nothing is reworded around a limit before the answer, and `designcrews` refuses builders whose tasks name more pages than the plan allows.
Framelink is the read path: a Figma personal token in `~/.config/figma-context-mcp/.env` (`FIGMA_API_KEY=...`, mode 600) and the MCP server added with `claude mcp add framelink-figma --scope user -- npx -y figma-developer-mcp --stdio --env ~/.config/figma-context-mcp/.env --no-telemetry`; `figma check` prints these lines when it cannot read; the token never goes on a command line.

**Reads and writes are split.**
The official Figma MCP caps calls per seat (Pro Full: 200 a day, 10 a minute) on tools that read; writes are exempt.
So `use_figma` (official MCP) is for WRITES ONLY, never a read-only script, and every write script returns the facts it set (node ids, variable bindings, component keys), so no read proves a binding.
Every READ goes through Framelink, which uses Figma's REST API and does not count against that cap: node trees for asserts and the judge, audits, and reviews through `get_figma_data` (or `compose figma tree`), and images through `download_figma_images` in place of `get_screenshot` and `get_metadata`.
`get_design_context` stays out of hand-off.
REST data covers structure, names, layout, sizes, positions, resolved fills, text, fonts, component properties, and component keys; it lacks variable bindings and the remote/library flag, so a binding is proved by the write's returned facts and library origin by component key match.
A `use_figma` script that sets nothing is a read, even when it only measures layout, sizes, or positions: measurements come from Framelink tree data (`get_figma_data` on the written nodes, or `compose figma tree`) after the write, and every builder brief says so.
The official connector takes `use_figma` and the `create_session` it needs, nothing else: never `whoami`, `get_libraries`, `search_design_system`, `create_new_file`, or `get_variable_defs`.
The connector rule stands: `mcp__claude_ai_Figma__*` or the Figma plugin's `mcp__plugin_figma_figma__*` only for writes, never another `plugin:*figma*` server.

**Read before any write.**
All read-only, in this order:
1. Linear: the ticket, its parents and children with their Decisions so far and acceptance criteria, and a `compose linear list --search` search in the project for "design system", "tokens", and "Figma".
2. The Frame0 wireframes, when `.compose/<slug>/design.f0` exists: `compose frame0 pages --project <slug>` reads the file without starting the app; to see a page, `compose frame0 up --project <slug>` right before, `compose frame0 export --project <slug> --page <page>`, and read the PNG it writes; an exported page stays in your context, so export it again only after it changed; `compose frame0 down --project <slug>` once read.
3. The repo's tokens, CSS, and components through trail: `trail ask "design tokens theme css variables" --source`, `trail grep "--color-"`.
4. `DESIGN.md`, when the repo has one.
5. Figma: a Framelink fetch of the stored file at depth 1, to see what the canvas has.

**Frame0 pages.**
Draw a flow's pages when you draw that flow, never a skeleton of every flow up front.
A new page for a journey goes right behind that journey's pages (`add_page` takes `after`, a page id), never at the end.
Before every review ask, run `compose frame0 lint --project <slug>` and fix what it names with `compose frame0 move|delete|links`.

**The ticket decides where it starts**, as 0j does for code:

| Given | Designer does |
|---|---|
| **epic** | Check for a design system (below). None: write the design-system epic with its features and stories, send its open decisions up as open questions, build Foundations once they are answered. One exists: continue at the first story not Done under it or under the epic's features. Design stories are lean: one flow's lowfi or one screen's hifi each, cut just ahead of the code story it unblocks, walking skeleton flow first, lowfi then hifi inside each flow. |
| **feature** | Its design system exists, or at least its Foundations are Done; else start there and link the feature `blocked by` it. Then one design story per screen or flow the feature's stories name, each with its design tasks. |
| **story** | The screens its acceptance criteria imply, as design tasks under one design story linked to it. |
| **design story, partly done** | Read its tasks' states (0s): fetch each In Progress task's tree through Framelink to see what the canvas has, cancel and re-split what failed, start builders for every Todo, review what is In Review. Nothing that passes its assert is rebuilt. |
| **loose idea** | Not the designer's: the engineering manager shapes it with the product owner (0b); the designer starts once the ticket exists. |

**The design system is its own epic.**
It is labelled `Epic`, titled `<repo> design system`, with three features, built in this order:
1. Foundations: color primitives, semantic color with Light and Dark modes (or the one mode a recorded decision names), spacing, radius, typography.
2. Components: one story per component family.
3. Hand-off: the foundations page and the exported tokens.
No component is built before the foundations it uses.
No screen is built before the core interaction model is settled: how the user moves through the product (the primary flow, the navigation, what one screen holds) is settled while shaping (0b) and `compose decide` records it as Decisions so far lines; a screen story cut before those lines exist is blocked until they do, and Foundations (the tokens) is the only design work that runs ahead of it.
A product feature links `blocked by` the design-system feature it needs, so its state rolls up true (0s).
The first version holds the tokens (color, spacing, radius, and type, in Light and Dark modes unless a decision says otherwise) plus only the components the next feature's screens need.
Record the epic's id in `.compose/<slug>/linear.json` as `"design_epic": "ENG-200"` so `compose sync` reads its features, their stories, and their tasks like the project feature's, and `designcrews` can start the design tasks.
Design task ids must differ from the project feature's task ids.
Whether a design system exists is checked in Linear (an `Epic` titled with "design system"), then in the Figma file (a Framelink fetch of the stored file: pages and top-level frames named for foundations, tokens, or components), then in the repo (`trail grep` for token files, `tailwind.config`, `tokens.json`).
Linear wins when they disagree; the disagreement is a `contradiction` report.
Every plan, story, and task the designer writes is a Linear issue; it writes no file in the repo.
A library publish is asked of the product owner only after `compose figma publish --project <slug> --library <file> [--keys <component keys>]` prints `publish: ask`: it reads the library's published components and styles and its last edit through the Figma REST API, so `publish: none` (nothing pending) means do not ask, and `publish: open` (an ask is already out, closed once the publish shows in the library) means add to it; when the product owner rules there will be no publish, `--withdraw` closes the ask and the line reads `none`.
At most one publish ask goes out per review round, batched with its other questions; the designer never asserts a publish is pending or done without that line.
Every open design decision goes up as an open question, one line under Not yet specified with a recommendation (`- Q1: <question> - Recommendation: <recommendation> - <why it matters>`), the question asked open with the options it weighs in the recommendation, never lettered options in the question, reported as `compose report --project <slug> --as <slug>-designer needs-user "<issue>: <n> questions <ids>; recommendation <one line>"`, text by default, on a Lavish page only when a picture decides it (a wireframe, a layout comparison, a diagram).
The designer never decides a product question.

**Visual direction.**
Before any screen story is built, the planning designer writes a visual direction for the surface as a Linear decision: anatomy, density and spacing measured from the research or competitors, status styling, and hierarchy.
Each rule cites research, a Linear decision, or a measured value.
Lowfi frames define flow and content only, never layout, spacing, or density.
A question that only follows the lowfi on a visual matter says so and gives the research-based alternative.

**Design tasks.**
A design task is a task issue (Task issue format) under a design story; its block adds `kind: design` and names `nodes:` in place of `files:`:

```compose
id: 012
kind: design
nodes: Buttons/Button
figma: <file key or url>   # optional: this task's own file; else the stored key
test: compose figma judge --project <slug> --only 012
```

`nodes:` names the page and the top-level frames or component sets the task may create or touch, as `<page>/<name>`.
One page per task, and two tasks never share a page, so builders work in parallel on one file; `compose tasks` warns `two design tasks own the same page`.
A design task is one component family, one token collection, or one screen state, built by one `use_figma` script that is safe to retry.
It holds at most one component set of 30 variants, and every call stays under Figma's 20 KB return limit.
`run` skips design tasks: they never clone, branch, or stack, and a passed one shows `passed`, never `merged`.
Linear is a design task's record: `compose status` shows a design task whose issue is In Review, or Done, on Linear (as last synced) as `passed`, with a note naming that state, whatever this checkout's `results/NNN.json` says, so a builder never waits on a task Linear has finished.
A design task the designer accepts by hand after the judge failed it is recorded with `compose done --project <slug> --only NNN --note "<why>"`, which moves it In Review and shows it `passed (hand)` at once; a task moved on Linear another way shows `passed` after the next `compose sync`.

**The gate.**
The red gate is the node tree as text, with screens of the same nodes beside it: Jev (1.13 on) reads images too.
The assert is the task's subtree as Framelink JSON: names, types, auto-layout, sizes, fills, variant properties, component keys, and text content, then what the write script returned (variable bindings, node ids).
`compose figma tree --project <slug> --only NNN --node <ids> [--bindings <file>]` fetches it through Framelink and saves it to `.compose/<slug>/results/NNN.tree.txt`; no one copies a tree by hand.
The same command renders each node through Figma's REST image endpoint (the Framelink token, scale 2, scale 1 for a node too big for 2) and cuts each render with jev's Pillow tool into PNG tiles of 280 to 1568 pixels a side in `results/NNN.screens/`, at most 6 images a task and 4 per tall frame; a render that fails saves no tree.
`compose figma judge --project <slug> --only NNN` asks Jev one MET, NOT_MET, or UNCLEAR question per acceptance criterion against that text, confirms each NOT_MET, writes `results/NNN.json`, and moves the task to In Review when it passes.
A tree over 30000 characters is judged in chunks cut along node boundaries, one request per chunk, each told it holds one part of the tree, so a node it lacks is UNCLEAR there, never NOT_MET.
Every NOT_MET a chunk gives is confirmed against the whole tree, so the confirm call sees a node another chunk holds; a tree over 120000 characters is confirmed chunk by chunk instead, each call told that a node missing from its part is no violation.
A confirmed violation in any chunk fails the criterion; a refuted NOT_MET is dropped, and the criterion is MET when a chunk shows it and no chunk's violation is confirmed.
A criterion no chunk can settle, because its nodes sit in different chunks, goes once to one call on the whole tree when the tree is at most 120000 characters; it is MET when that call quotes a node for every part of it, and `whole_tree` on the criterion records the answer.
A chunk that errors blocks the task; `results/NNN.json` records `chunks`, and each criterion's per-chunk verdicts as `parts`.
Jev first sorts the criteria on their text alone, with no screens: one a picture surely decides (0.9 or more) goes to the screens, and one about names, tokens, styles, bindings, component keys, auto-layout settings, or exact sizes and hex values stays with the tree alone, since shown screens Jev judges those by the look.
The look criteria go to the screens in one separate Jev request, which judges what a picture shows (text cut off or overflowing, overlap, misalignment, a missing element, unreadable contrast, a look the criterion contradicts).
A screen NOT_MET at the threshold is asked again on its own and fails the criterion only when Jev gives it both times; a screen MET settles a criterion the tree left UNCLEAR; the screens never lift a violation the tree confirmed.
A node with no screen is named in the rules, so its absence from the screens is UNCLEAR, never NOT_MET; a screen request that errors blocks the task; a task with no saved screens is judged from the tree alone and says so.
Before the builder runs there is no tree, so the test is red.
The look check beyond the criteria is separate: a `design-review` teammate takes one Framelink image (`download_figma_images`) per story, and a finding counts only once confirmed by quoting the node it saw.
The official MCP's read budget is small (200 a day and 10 a minute on the Pro Full seat), so no read goes through it, and images stop at one per story.

**The crew.**

| Teammate | Does | Model |
|---|---|---|
| `designer` | Reads the inputs, writes the Linear issues, starts the builders and the reviewer, runs the gate, hands off, reports up | `models.crew.designer`, else Opus 5.5 at high effort |
| `design-NNN` | One design task: builds it with a `use_figma` write script, saves the tree with `figma tree`, runs the task's `test:`, reports `working "design ready: <node ids>"` | `models.crew.design`, else `default` |
| `design-review` | One Framelink image per story; findings confirmed by quoting nodes | `models.crew.design`, else `default` |

Every session loads the `figma:figma-use` skill before every `use_figma` call.
The designer syncs (step 2), then starts every builder at once with `compose designcrews --project <slug>`: one `design-NNN` per design task not Done, Canceled, In Review, or already passed or done by hand (its result file, even before the next sync), and with no builder running, in the project worktree with no branch.
A design task waits until every task it is blocked by is In Review or Done.
`--only` picks tasks and `--print` shows the briefs, as with `testcrews`.
It starts at most 3 builders (`--max N`, or `design_concurrency` in verify.json; never the config's `parallel`) to stay under Figma's per-minute write rate limit, prints the queued ids, and the designer runs `designcrews --only <those ids>` as earlier builders report done or design ready.
It starts the reviewer like any teammate: `compose crew start --project <slug> --role design-review --title design-review --brief -`.
A builder reports `done` only when the designer says so.

**Hand-off to code.**
1. Every variable carries code syntax, and a groundwork task exports the variables to the repo's token file (`tokens.css` or `tokens.json`) from the write scripts' returned bindings, as code, before `run`.
2. The code task that builds a screen node names it on a `figma_nodes:` line in its compose block, one node per task; `run` writes the node's Framelink JSON into the task's clone for the implementer, who has no Figma tools, so its brief never carries the JSON.
3. Code Connect stays out until the Figma plan changes; it needs the Organization plan.
