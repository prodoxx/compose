### 7. Escalate and clean
A task that exhausts its attempts comes back with its full log.
Read the log first: the last attempt's test output and the implementer's last reply say what it missed.
A log that shows a fact the brief lacked (which file, which signature, what a value looks like) is a brief gap, not a task too big: add the fact to the brief inside `compose change start --why "<one line>"` and `compose change done` (sync first, step 8), then `compose run --only NNN` once more.
A log that shows the implementer had the facts and still missed is a split: write two or three smaller tasks that each name the exact function, file, and behavior the log shows it missed, have the test-writing teammates give each its own red test, and dispatch those.
Never re-dispatch a task unchanged, and never take the keyboard just because an attempt failed.
The exhausted task's issue is Canceled with a comment pointing at its replacements; the new tasks get their own issues, blocked by whatever the old one was blocked by.
The re-split is a change of course: sync, then `compose change start --why "<one line>"` before you edit Linear, and sync, then `compose change done` after (step 8).
When the blocker is not the task (fast provider down, or task not smaller than one function), the work still goes to a teammate, never your keyboard: set `model: claude` in the task's block and `run --only` it, or brief a teammate session for it.
Work teammates did outside `run` is recorded with `compose done --project <name> --only 024,025 --note "provider out of credit; done by <slug>-<role>"`, so `compose status` shows the truth, and the report says so.
That includes a teammate's commit on top of a passed layer: the layer stays in the stack, and a later `run` keeps a hand-done branch as it keeps a passed one, unless `--redo`.
A rebase conflict while stacking (`after: ... could not be chained`) is teammate work too: brief one with the two branches and the conflicting files.
The run goes on without that task: it is `unchained`, later tasks are blocked by it, and `run` or `resume` starts it once the chain rebases.
`compose status --repo <path>` shows every project with each task's state, attempts (spent ones: a rate-limit or busy-provider wait costs none), time, cost, and stack layer; use it to report progress instead of describing it from memory.
`compose watch` is how you wait for it to change.
`compose land --project <slug>` merges the submitted stack bottom up (`gh pr merge` per PR, each next layer rebased and retargeted onto the base, required checks awaited; a PR in a GitHub stack merges through the asynchronous merge API and GitHub moves the next layer itself); it is the only merge you run, never `gh stack merge`.
Without `--yes` it prints the plan and changes nothing; add `--yes` only after the user said to land.
A stop names the PR; fix it and re-run.
When only some layers were submitted it lands those and ends with a `land   left` line; the rest rebuild on the base at the next `compose stack --submit`.
`compose clean --project <slug>` is the post-merge step (never repo-wide: that touches every project), run after the reviewer has merged PRs on GitHub (or the user merged locally): it fetches, removes task clones and the CLI's stack worktree, deletes task and layer branches that are proven merged, and once every layer and the project branch are merged it removes the project's worktree and branch too.
It moves Linear first, and never removes a worktree someone stands in: run from inside the project worktree, or before the team lead reported done, it keeps the worktree and project branch and says why.
The team lead's `done` then removes them when its turn ends (inside herdr), or names the `compose clean` to run from outside; `--project <slug> --force` removes them under a team lead, never under the command itself.
Branch deletion that compose has proven merged is reversible housekeeping, so run `compose clean --project <slug>` without asking the product owner, also while teammates are still working.
With live crew it removes only the task and layer branches proven merged (a branch a teammate's clone still has checked out stays), names every unproven branch as kept, and leaves slots, task clones, the stack worktree, and the project worktree and branch alone, because the crew stands on them.
`--project <slug> --force` is what removes those too, and `--force`, `--delete-unmerged`, `--delete-remote`, and `--abandon` stay asks.
`compose clean --abandon --project <slug>` drops an unmerged project the product owner gave up on, and only with that flag: it lists what it removes (worktree, local branches, herdr tabs, results) and what stays (Linear, pushed branches), then removes them; `--dry-run` only lists, live crew needs `--force`.
Cancel its Linear issues yourself.
A branch counts as merged into a target when it is contained in the target, when every commit on it has its patch in the target (`git cherry`), when merging it into the target would change nothing (`git merge-tree --write-tree` gives the target's own tree without a conflict, which covers a stack re-cut onto a moved base), or when a merged PR on GitHub names it (which also covers squash and rebase merges).
Any doubt means not merged.
Task and layer branches are checked against the layers' review base (`review_base` in verify.json) and its remote first, then the trunk, its remote, main, and master.
Unmerged work is kept and named: each kept branch, the project branch included, gets one line, `clean  <branch>: kept unmerged, first unmatched commit <short sha> <subject>`, with ` and <n> more` when there are more.
It never deletes unmerged layers unless `--delete-unmerged`.
Run it whenever the user says PRs were merged, and at the end of a feature.
It also keeps Linear true (0s) with the workspace's key: every task proved merged moves to Done, its story rolls up, and the feature is Done once every story is and the project branch is merged; a Canceled task stays Canceled.
You move none of these yourself; the epic rolls up from the feature as 0s says.
Without a key it prints one `linear skipped` line, and the states are yours until the key is set.
A task done by hand (`compose done`) is proven merged the same way and goes to Done with the rest.
