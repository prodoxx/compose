### 1. Plan from the spec
The planner teammate writes the plan; the team lead reviews its cut at 3b instead of writing it.
Input: the feature issue's Intent, My calls, and Decisions so far, plus `DESIGN.md`, a PRD, whatever the repo already had.
Read all of it.
Write the plan for an implementer who has not seen the codebase and will not ask: the plan is the set of decisions that implementer cannot make alone, so every such decision is in it, and nothing it can read off the named files is.
The plan is a `## Plan` section in the feature issue's description (`compose linear update <feature> --section "## Plan" --file <path>`), never a file in the repo.
The planner session starts with skills off, so every skill it needs is read as a file.
Draft the whole Plan and any Decisions text before saving.
Save with few `compose linear update --section` writes, one per section: `--section "## <heading>"` replaces that whole H2 section, so write the full section text.
To rename a section, start the text with its new `## ` heading; an empty body removes the section.
Put task detail on the task issues, not on the feature issue.
The planner never re-reads an issue it just wrote: `compose linear update` prints only `updated <id>`, so the write is the proof.
`<project>` is a short slug for this piece of work (one repo can hold several); `.compose/<project>/linear.json` holds `{"feature": "<feature issue id>"}` and is how the CLI finds the plan and the tasks.
The plan opens with a header: Goal (one or two sentences), Architecture (how the pieces fit, one paragraph), Global constraints (what every task must respect: the simplicity bar, no new dependencies, naming, the test runner), and Review focus (the five inputs or conditions the design implies but no test yet exercises that are most likely to bite a user, most likely first, each one then pinned by a test in the task that owns its code).
Then a file map: every file the feature creates or changes, one line each with its responsibility, before any step.
Then numbered steps, each with the files it touches, the exact signature or export it adds, the test that proves it, and the steps it depends on.
A step holds code only where the implementer could not derive it: an algorithm the spec leaves open, exact copy, a fixed data shape; everywhere else one line of description beats a pasted function body.
An unknown the plan cannot settle (does the library support it, how slow is the query) becomes a spike: a probe task whose deliverable is the answer, written to the issue's Notes, never a code task that guesses.
Before the cut the planner reads its own plan once as the implementer will: every acceptance criterion maps to a step, no step names a file the file map lacks, a type or signature means one thing in every step that uses it, the Review focus names a test or step that covers it, and the plan is no longer than the feature needs.
Decisions already made in the spec are not reopened.
The plan states the product owner's quality bar up front, as acceptance criteria on the stories and tasks it touches, never a later polish wave:
- anything user-facing looks finished and pixel-picky: spacing, alignment, readable type, and styled loading, empty, error, and success states
- the app builds and starts on the current toolchain (the 0g smoke checks stay green)
A second wave for polish or a toolchain fix the first wave could have seen is a planning miss.
Stories are lean: each is the thinnest slice that works end to end and unblocks the next story, with at most 5 criteria.
Split cues in a story: "all", "every", several When/Then pairs, or several outside systems.
When no split fits, a time-boxed probe answers the unknown first, then the split.
The plan also states the simplicity bar, and every layer review holds the code to it:
- the simplest code that meets the requirements: no hardening, defensive flags, helpers, or extras the requirements do not ask for (signal handling, closed-state guards, retry layers)
- no wrapper scripts or shims when pinning a version or a documented setting works
- acceptance criteria name the required behavior and its real edge cases, never hardening beyond the requirements
A task is the smallest unit that carries its own test and is worth its own review: setup, configuration, and docs fold into the task whose deliverable needs them.
The planner creates the stories with `compose linear create`, in ship order, and reports `working "stories <issue>: <n> created: <titles>"`; nobody waits for a go, and an edit the product owner asks for is applied by the team lead (a change of course once anything is dispatched, step 8).
The plan's `## Design facts` (deliberate choices a reviewer might flag: a single DB connection, credentials from env, stdout as the log) go into `verify.json` `review_context` now, before the first verify, so review never re-litigates them.
When the feature has a prototype or design reference, the plan lists what must match it, per screen: icons, copy, loading and empty states, lengths, spacing.
Each screen becomes a `prototype` entry in `verify.json` (6), so the match is checked right after `run`, not at the first verify.
