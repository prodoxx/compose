### 6. Verify
`compose verify --repo <path> --project <name>` is the local no-mistakes-style pipeline.
Nothing is pushed; only network calls are model APIs.
Stages, in order, from `.compose/<project>/verify.json`:

```json
{
  "checks": ["uv run ruff check .", "node --test 'tests/**/*.test.js'"],
  "docs": ["README.md", "DESIGN.md"],
  "perspectives": ["correctness", "security", "spec", "docs"],
  "jev_acceptance": true, "acceptance_threshold": 0.6, "acceptance_gate": false,
  "e2e_setup": "cd ... && python -m server.server", "e2e_setup_wait": 3, "e2e_env": {"API_KEY": "..."},
  "e2e": [{"name": "greenhouse fill", "url": "https://...", "goal": "Fill the application ... stop before Submit.",
           "assert": "python scripts/check_greenhouse.py", "prices": {"typesafe_per_call": 0.0}}],
  "review": true, "review_base": "main", "fix_model": "pi:openrouter-fast/z-ai/glm-5.3-flash@preset/glm-5-3-flash-fast",
  "review_context": "Design facts reviewers must respect, e.g. test credentials come from env by design and never reach the server."
}
```
e2e runs alongside review and jev acceptance, right after checks, since those two only wait on model calls.
Each e2e stage gets two fresh free ports, `$E2E_PORT` and `$E2E_CLIENT_PORT`, in the environment of `e2e_setup`, `setup`, `driver` and `assert`, and expanded in every value of a case (`url`, `goal`, its `env`) and in `e2e_env`.
Use them; never hardcode a port, unless the app pins one (then keep only that one fixed).
Start servers in `e2e_setup` with a plain `&`; never free ports there with `lsof | kill`.
Cases start once every port `e2e_setup` names accepts a connection (up to 60 s, or `e2e_setup_wait` if longer); a setup naming neither port, like an extension's browser on a pinned port, waits a fixed `e2e_setup_wait`.
A case's own `setup` and `setup_wait` work the same way.
A case's `setup` (jev or driver case) starts before that case and ends after its `assert`, for example to log in a different user.
e2e driver and assert scripts live in the project, under `.compose/<slug>/e2e/`, referenced by that path in `verify.json`; verify's worktree links the project's `.compose`, so they resolve there.
Never put them in `~/.compose`, `/tmp`, or anywhere outside the project: teardown and `clean` cannot find them.
Each e2e stage also launches its own `bp` Chromium on a third fresh port with a throwaway profile, and sets `BU_CDP_URL` and `BU_NAME` for `driver`, `assert` and jev.
Verify never attaches to the user's real Chrome; no project launches a browser in `e2e_setup` for that.
The stage's browser is headless: an unattended verify runs while the display sleeps, and a headed Chromium then stops painting.
`"e2e_headed": true` shows it; on macOS verify keeps the Mac awake with `caffeinate` for its whole run, headed or not.
A stage whose `e2e_env` sets `BU_CDP_URL` itself (an extension's Chromium, see 6a) uses that browser.
A project whose cases need no browser (`driver` cases for a terminal app) sets `"e2e_browser": false`: the stage starts none and sets no `BU_CDP_URL`.
The stage ends everything it started, pass or fail: the setup's process group, its browser and that browser's harness daemon, and anything left listening on its ports or the CDP port.
No server or browser outlives a round.
A SIGTERM or SIGHUP to verify ends them too; the next stage ends the browser of a verify killed outright.
A harness failure (jev or browser crash, missing tool, port in use) is reported as `TOOL ERROR`, retried once, and never handed to a fix round; only app failures are.
1. **checks**: lint, unit tests, and the 0g smoke checks, exact and cheap, run first.
  Formatting is done: `run` formats each passed task's own files (gofmt, the repo's installed prettier) before committing, and keeps the unformatted version if formatting would break the test.
   Only the first round runs every check up front.
   A fix round runs the `test:` commands of the tasks whose files its fix changed (`check  scope` line), then the full checks once, only after every other stage passed (`check  full` line).
   A fix that changes a file no task names runs the full checks instead.
   A check, the full suite, or a task's `test` already green on the same git tree (the files, not the commit) with the same command is not run again.
   Verify, the run's pass gate, and `compose stack --submit` all skip it and print `<check> green on tree <sha12> at <time>, not rerun`.
   A red or unknown result is never reused.
   `compose verify --fresh` runs every check anyway.
   After a rebase or a stack rebuild, run one full suite on the top of the stack and the final verify, never a per-layer suite.
   A lower layer's tree differs, but its own tasks' tests already passed in the run.
   The submit gate checks them again only where no green result matches.
2. **review**: parallel reviews by `models.review` in the config (a `claude:` id runs Claude Code; unset, the `.env`'s `TEXT_MODEL`, Mercury 2.5 by default), one per perspective, then a confirmation call per high or medium finding, which must quote the wrong line and say how it must read (a line that must read as it already does is no defect).
  Unconfirmed findings are dropped and shown as dropped.
  Only confirmed highs fail the stage.
3. **jev acceptance**: every bullet under `## Acceptance criteria` in every task issue becomes one choice question to Jev (TypeSafe): MET, NOT_MET, UNCLEAR, with probabilities, one request per task against that task's own files, then a confirmation call per NOT_MET. Advisory by default, since tests already cover every criterion; set `acceptance_gate: true` to make confirmed NOT_MET fail the stage.
4. **e2e**: each case drives the stage's own browser with jev (`jev/`) to the goal, then runs `assert`, an independent check (written by the test-writing teammates) that reads the real DOM or run log.
  A model's DONE is never proof.
   The `assert` runs after every jev run, also one that gave up or crashed, so an assert that resets the app for the next case always runs.
   It checks the app is in the state the case needs (signed in, no overlay, seed present) before it checks the feature: when the feature's part is absent it prints a line starting `ASSERT FAILED` and exits non-zero, which `--prove` takes as "feature missing" without asking a model; when it cannot tell, it exits non-zero without that line.
   A form login needs a password jev never sends to a model: give the case `"secrets": {"Password": "$E2E_PASSWORD"}`, keyed by the field's label, with the value in the environment (`e2e_env`, `~/.compose/.env`); jev types it itself.
   Without one, jev skips the password field and says so in its stop reason.
   A jev run that misses its goal shows its stop reason on the `e2e` line, the page it stopped on, and its last steps; `results/verify.json` keeps every step, and `results/e2e/<n>-<case>/` its step screenshots.
5. **fix loop** (`--fix N`, default 2): confirmed findings go to the fast implementer in the repo itself, protected files are reverted if touched, the files the fixer changed are committed (never the agent wiring a session hook rewrites, nor a check's leftovers; your own uncommitted changes skip the fix), and every stage runs again, with checks scoped to the fix as in 1.
  A fixer has the tasks' scope: a round that touches any file the stack does not already change and no task names in `files:` (a lockfile, `setupTests.js`, a new `package-lock.json`) is reverted whole and verify ends FAIL. A round that changes no failing check and removes no cited line is discarded the same way, unless it adds code for a confirmed finding in a file that finding names and its own new test fails without the fix and passes with it.
  Treat that FAIL as an environment problem for a teammate, not a finding.
  After N rounds it escalates to you with the findings.
  A finding that contradicts a Design fact or a Decisions so far line is not a defect and never a fix round: rule on it once by adding the fact to `review_context` in verify.json (one sentence, with the decision's id), then re-run; review reads it and never raises it again.
  The findings that reach you after N rounds get a ruling each in the wake that brought them: a task, a `review_context` line, or an open question on the issue (0h) only when one reopens a product decision.
  `--fix 0` reports only.

Every line prints its clock time and duration.
The last line is the cost ledger: dollars and tokens per provider (openrouter for implementers, fixes, OpenRouter reviews, and jev's text helper; claude-subscription for Claude Code calls; cerebras when a task pins it; typesafe for Jev decisions) and the total.
`+?` after a provider means tokens were counted but no price is set; set `prices` in verify.json.

Three modes of `compose verify` run part of the pipeline, besides the `--skip-*` smoke runs:
- `--prove` (before `run`, step 3): every e2e case against the project branch must fail only because the feature is missing.
  A failure is classified from jev's stop reason, last steps and screenshots (rules first, then a fast model); environment failures, a passing case, and a page whose cases only force a variant in the URL fail it.
  Writes `results/prove.json`, which `run` requires: it refuses until a prove passed on the current cases and setup (`--unproven` overrides).
  A case that forces a variant on purpose says why in `"url_override": "<why>"`.
  After a re-plan the stack holds layers, so it refuses; `--prove --only <ids to redo>` proves the cases on the stack below the first of them.
- `--review-only` (right after `run`, step 5): the review and jev acceptance, no checks, e2e or fixes.
  Writes `results/review.json`, never `verify.json`.
- `--prototype` (right after `run`): drives jev to each `"prototype": [{"name", "url", "goal", "reference", "must_match": [...]}]` screen of the built app and writes `results/prototype.md`, a checklist of each `must_match` line next to the screenshot (`results/prototype/e2e/`) and the reference.
  It fails only when a screen cannot be reached; you tick the lines.

Fix what fails, re-run.
Only then tell the user it is done, with the verify output.
Then write each layer's PR text and show the `compose stack` preview with it (step 4).
