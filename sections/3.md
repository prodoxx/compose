### 3. Write the tests first (red)
The acceptance tests are the contract, so you specify every one, but teammates write them, one per task, all at once.
The groundwork teammate lays the ground first (0g): schema, codegen, stubs that compile, the e2e cases, and a contract file (`.compose/<slug>/results/contract.md`, never committed) that pins every type, signature, value-or-pointer shape, fixture, and test path a test writer would otherwise guess.
Implementers never see the contract: each task brief states every signature and exact line its test asserts, the contract copies them, and a test asserts nothing only the contract gives (`spec-check` fails a brief that points at it).
When it reports `stubs ready`, run `compose testcrews --project <slug>`: one `tests-NNN` teammate per task (the `tests` or `groundwork` model under `models.crew`), each briefed with its task issue, the holdout rule below, its `protected:` path, a line budget, and the contract. `--print` shows the briefs; `--only` picks tasks; `--redo` takes passed tasks too, for a re-plan that changed their briefs (8, Re-plan).
Each test-writing teammate works in its own worktree on its own branch (`<project branch>-tests-NNN`, off the stubs commit), so no teammate can amend or reset another's commit.
Tasks that share a protected test file get their writers one after another: a later one waits until the earlier writers of that file are collected, then `--collect` starts it off the project branch that holds their tests, so no two writers create or append to the same file.
A file a writer only reads orders nobody: one already on the project branch that its task's `test:` command does not run (groundwork's pins, say).
The budget is 60 lines per task by default; `--budget N` changes it for the whole set, and `test_lines: N` in a task's block wins for that task.
When a test is accepted, `compose testcrews --project <slug> --collect` cherry-picks the commits of each teammate that reported `test ready` (or `done`) onto the project branch in task order and removes their worktrees and branches.
It skips a teammate that has not reported `test ready`, keeping its branch and worktree, since returning its worktree ends the session still in it.
A conflict keeps that teammate's branch and worktree, the others are still collected, and the collect exits naming every conflict.
`run` also collects any finished test teammate's branch before it starts, and refuses to start while a test teammate is still writing or waiting to start.
Parallel writers without the contract guessed shared types differently and wrote tests that fail on correct code; with it, writing every test takes about as long as writing one.
Groundwork that is real code, not a stub, is a task of its own (`000`) for `run`, not part of any brief.
For anything with a UI or a server, the browser e2e (the `e2e_setup` and `e2e` cases in `verify.json`, each with an `assert` that checks the real DOM or log) comes from the groundwork teammate, before `run`, so the first verify drives the finished app; never "add e2e after the run".
Prove those cases before `run`, once the tests are collected: `compose verify --project <slug> --prove` runs every e2e case headless against the project branch as it is before `run` (its own setup and seed).
Each must fail, and only because the feature is missing.
`run` refuses until a prove passed on the current cases and their setup; `--unproven` overrides that only when the product owner says so.
A case that fails for the environment (page did not load, login failed, a cookie banner or tour in the way, seed missing, wrong path) or that already passes fails the prove step with the reason; fix the case, the seed or the setup first, since such a case fails every verify and no implementer can fix it.
Every variant of a flag or experiment needs at least one case that reaches it through the real flag or assignment path (a seeded user, the flag service), never only a URL override; `--prove` flags a page whose cases all force the variant in the URL, and a case that must force it says why in `"url_override": "<why>"`.
Each test teammate reports `working "test ready"` once its file is committed, not `done`, since `done` closes its tab.
Read every test once they are all in (`git log -p HEAD..<project branch>-tests-NNN`), send changes back with `herdr agent prompt <slug>-tests-NNN "..."` until each tests what its issue says, then tell each to report `done` and run `--collect` before `run`.
A test that fails on the stubs because it needs code another task owns is a missing dependency: give the task `after: <that task>` before dispatch, or the implementer can only pass by editing a file outside its scope (one task's open test needed another's seed code and was rejected for scope three times).
Every test run has a hard time limit, whatever the language: the CLI runs each task's test command under 120 s (`test_timeout:` in the task's block changes it), and implementers never run it: the CLI runs it after each implementer turn. Teammates run tests through `compose timed <seconds> -- <command>`, only the tests of what they changed while they work and the whole suite once before they report `done`; a `-k` filter or one test file has a quick lane of its own and never waits on a suite. A hang kills the whole process group and fails with exit 124 and a deadlock hint, costing seconds, not minutes.
jev e2e cases run on the same leash: 150 s per case (`timeout` on the case changes it), the whole group killed at the limit. A jev that times out, ends blocked, or runs out of actions is a harness failure (`JEV_GAVE_UP`): retried once, reported, never handed to the fixer. If it repeats, check the flow by hand in the browser before blaming the app.
List each test under `protected:`. The CLI rejects any attempt that changes a protected file, and `run` refuses a task whose protected test is not on the project branch yet. A task whose proof is its `test:` command alone (a config or tooling task with no test file) may leave `protected:` empty: no writer starts for it, and `run` checks only the paths a task names.
It must fail on HEAD; `run` refuses a task whose test already passes.
Tests are proportional to the code they test:
- one test file per unit under test (a component, a resolver, a store), extended in place by later tasks and waves; never a new file per wave or per fix (`Questions.again.test.js`, `styles.polish.test.js` are wrong)
- they cover the behavior the requirements name plus its real edge cases; never CSS values, contrast math, or tooling wrappers (unless the wrapper is the deliverable), and never tests that assert dependency lists, lint or tool configuration, or the contents of a config file
- test code stays in the same order of magnitude as the product code; the test-writing teammates are briefed with this and you send back anything bigger
Include holdout cases the task issue does not list. The implementer is told they exist, so it has to implement the behavior rather than the examples. The deny-list task showed why: given only the listed labels, the fast model wrote one literal regex per label.
Commit the tests before dispatching; independent tasks branch from HEAD, stacked tasks from their lower layer.
The tests sit on the project branch only while the work runs.
When the stack is built, each task's test commits move into that task's review layer (a commit whose files are all in one task's `protected:`; when several tasks protect them, the task whose test writer `tests-NNN` made it), so the tests are reviewed with the code they prove; everything else on the project branch is groundwork (step 4).
