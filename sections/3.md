### 3. Write the tests first (red)
The acceptance tests are the contract: you specify every one, teammates write them, one per task, all at once.
The groundwork teammate lays the ground first (0g): schema, codegen, stubs that compile, the e2e cases, and a contract file (`.compose/<slug>/results/contract.md`, never committed) that pins every type, signature, value-or-pointer shape, fixture, and test path a test writer would otherwise guess.
The contract is compact: shared sections first (types, stubs, helpers), then one `## task <id>` section per task (e.g. `## task 001`) holding only that task's test path, names, command, and fixtures.
Each writer's brief carries the shared sections and its own task section, never another task's.
Implementers never see the contract: each task brief states every signature and exact line its test asserts, the contract copies them, and a test asserts nothing only the contract gives (`spec-check` fails a brief that points at it).
When it reports `stubs ready`, run `compose testcrews --project <slug>`: one `tests-NNN` teammate per task (the `tests` or `groundwork` model under `models.crew`), each briefed with its task issue, the holdout rule below, its `protected:` path, a line budget, and its slice of the contract; `--print` shows the briefs, `--only` picks tasks, and `--redo` takes passed tasks too, for a re-plan that changed their briefs (8, Re-plan).
Each test-writing teammate works in its own worktree on its own branch (`<project branch>-tests-NNN`, off the stubs commit), so no teammate can amend or reset another's commit.
Tasks that share a protected test file get their writers one after another: a later one waits until the earlier writers of that file are collected, then `--collect` starts it off the project branch that holds their tests, so no two writers create or append to the same file.
A file a writer only reads orders nobody: one already on the project branch that its task's `test:` command does not run (groundwork's pins, say).
The budget is 60 lines per task by default; `--budget N` changes it for the whole set, and `test_lines: N` in a task's block wins for that task.
A writer's `test ready` report starts its own collect: once that writer's turn ends, compose runs `testcrews --collect --only NNN` itself, which cherry-picks its commits onto the project branch, removes its worktree and branch, frees its slot, writes its `done`, closes its tab, and wakes you.
You never wait on a writer or collect by hand inside herdr; `compose testcrews --project <slug> --collect` does the same for every ready writer outside herdr, or after an auto-collect failed (it reports `blocked` as the writer, with `results/collect.log` to read).
It skips a teammate that has not reported `test ready`, keeping its branch and worktree, since returning its worktree ends the session still in it.
It also skips one that reported `test ready` but is on a turn again (a correction you sent it), and takes it once it is idle.
Before it collects a test, it runs the task's `test:` command in the writer's worktree.
A test that fails because it cannot load (an ImportError, a missing module or name, a syntax or compile error), not for the missing behavior, goes back to its writer once, with the error, through `herdr agent prompt`.
The collect leaves that branch alone until the writer reports `test ready` again.
A test still broken after that one send back, or whose writer is not running, is collected with a warning.
A conflict keeps that teammate's branch and worktree, the others are still collected, and the collect exits naming every conflict.
`run` also collects any finished test teammate's branch before it starts, and refuses to start while a test teammate is still writing or waiting to start.
Parallel writers without the contract guessed shared types differently and wrote tests that fail on correct code; with it, writing every test takes about as long as writing one.
Groundwork that is real code, not a stub, is a task of its own (`000`) for `run`, not part of any brief.
For anything with a UI or a server, the browser e2e (the `e2e_setup` and `e2e` cases in `verify.json`, each with an `assert` that checks the real DOM or log) comes from the groundwork teammate, before `run`, so the first verify drives the finished app; never "add e2e after the run".
Prove those cases before `run`, once the tests are collected: `compose verify --project <slug> --prove` runs every e2e case headless against the project branch as it is before `run` (its own setup and seed).
Each must fail, and only because the feature is missing.
`run` refuses until a prove passed on the current cases and their setup; `--unproven` overrides that only when the product owner says so.
A case that fails for the environment (page did not load, login failed, a cookie banner or tour in the way, seed missing, wrong path), or already passes, fails the prove step with the reason; fix the case, seed, or setup first, since such a case fails every verify and no implementer can fix it.
Every variant of a flag or experiment needs at least one case that reaches it through the real flag or assignment path (a seeded user, the flag service), never only a URL override; `--prove` flags a page whose cases all force the variant in the URL, and a case that must force it says why in `"url_override": "<why>"`.
Each test teammate reports `working "test ready: <commit>; holdouts: <cases>"` once its file is committed, never `done`: the collect writes its `done`.
Review each test on the project branch as its `done` arrives (`git log -p <stubs commit>..HEAD -- <its protected path>`), while the other writers go on.
A test that does not test what its issue says is replaced, never hand-edited: fix the issue if the brief was the gap, then `compose testcrews --project <slug> --only NNN --redo`, which starts a fresh writer off the project branch told to rewrite it.
A test that fails on the stubs because it needs code another task owns is a missing dependency: give the task `after: <that task>` before dispatch, or the implementer can only pass by editing a file outside its scope (one task's open test needed another's seed code and was rejected for scope three times).
Every test run has a hard time limit, whatever the language: the CLI runs each task's test command under 120 s (`test_timeout:` in the task's block changes it), and implementers never run it: the CLI runs it after each implementer turn.
Teammates run tests through `compose timed <seconds> -- <command>`: only the test files of what they changed, never the whole suite, which verify runs; a `-k` filter or one test file has a quick lane of its own and never waits on a suite.
A hang kills the whole process group and fails with exit 124 and a deadlock hint, costing seconds, not minutes.
jev e2e cases run on the same leash: 150 s per case (`timeout` on the case changes it), the whole group killed at the limit.
A jev that times out, ends blocked, or runs out of actions is a harness failure (`JEV_GAVE_UP`): retried once, reported, never handed to the fixer.
If it repeats, check the flow by hand in the browser before blaming the app.
List each test under `protected:`.
The CLI rejects any attempt that changes a protected file, and `run` refuses a task whose protected test is not on the project branch yet.
It must fail on HEAD; `run` refuses a task whose test already passes.
Tests are proportional to the code they test:
- one test file per unit under test (a component, a resolver, a store), extended in place by later tasks and waves; never a new file per wave or per fix (`Questions.again.test.js`, `styles.polish.test.js` are wrong)
- they cover the behavior the requirements name plus its real edge cases; never CSS values, contrast math, or tooling wrappers (unless the wrapper is the deliverable), and never tests that assert dependency lists, lint or tool configuration, or the contents of a config file
- test code stays in the same order of magnitude as the product code; test writers are briefed with this and you send back anything bigger
Include holdout cases the task issue does not list.
The implementer is told they exist, so it has to implement the behavior rather than the examples.
The deny-list task showed why: given only the listed labels, the fast model wrote one literal regex per label.
Commit the tests before dispatching; independent tasks branch from HEAD, stacked tasks from their lower layer.
The tests sit on the project branch only while the work runs.
When the stack is built, each task's test commits move into that task's review layer (a commit whose files are all in one task's `protected:`; when several tasks protect them, the task whose test writer `tests-NNN` made it), so the tests are reviewed with the code they prove; everything else on the project branch is groundwork (step 4).
`testcrews --collect` refuses a writer whose commits touch a file only another task protects, names that file and task, and keeps the writer's branch: the commit would land in the other task's layer and fail its `test` there, so give each task its own test file.
