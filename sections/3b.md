### 3b. The task list goes to the product owner; it waits only when it departs from the scope they settled
`compose spec-check --project <slug>` runs before `compose tasks`.
A story with no task issues always fails spec-check: groundwork alone never finishes a story.
Work that is not code (a manual browser run that needs the product owner's sign-in) stays teammate work, but the story's code, dependency, and toolchain changes are still tasks.
Run `compose tasks --repo <path> --project <name>`: the stack order of the tasks still to land (bottom first, a task above its `after:` tasks, then by id: the order the stack gets), every task's id, title, the files it owns, what it builds on, and its test, then the run waves of the tasks still to run, with a warning for any file two tasks claim, any task whose brief names a file another task owns without an `after:` on it (the warning gives the `after:` to add), any task too big, and a serial chain (which also exits 1).
Fix every WARNING first.
Compare the list with the spec the product owner settled (the feature issue's Decisions so far and the stories):
- **It matches** (it builds exactly the settled scope, with no new or dropped scope, no dependency bump or toolchain change the product owner did not settle, no decision the product owner has not made): report `working` with the `tasks` output and one line per task on what its holdout cases cover, and dispatch right away.
  The product owner can still stop it from the report.
- **It departs in a reversible way** (a dependency bump or toolchain change the product owner did not settle, a decision they have not made, all of it undone by redoing tasks nothing has been pushed from): rule on each, `compose decide --project <slug> --ruling --new "<departure and what you chose>"`, report `working` with the `tasks` output and one `ruled: D<n> <decision>` line per departure, and dispatch right away.
  The product owner can still stop it or overturn a ruling from the report.
- **It departs in scope** (a story or scope added or dropped): report `needs-user` with the list, each departure named, and your recommendation, and dispatch only after the product owner's go.
The product owner may combine, split, reorder, re-own, or drop tasks, here or in Linear, before or during a run.
Apply the changes to the task issues (a dropped task's issue is Canceled and loses its `compose` block), re-run `compose tasks`, and re-run what changed.
When the product owner has said to review every task list, the gate is always a stop.
After the first dispatch, those edits are a change of course: sync, then `compose change start --why "<the product owner's words>"` before you edit Linear, and sync, then `compose change done` after (step 8).
Green is the implementer's job.
Refactor goes through review and the verify fix loop, whose fixer is the fast model; never the implementer refactoring its own green code, and never you typing it.
