### 4. Dispatch
`compose run --repo <path> --project <name>` runs tasks in dependency order: independent tasks in parallel, one clone and one implementer session (pi by default) each; a task with `after:` starts as soon as that task passes, on top of its branch.
The implementer edits and ends its turn without running anything; the CLI then runs the task's test itself.
Test failures, an over-limit diff, a new document, or a change outside `files:` are fed back into the same session up to `--attempts` (default 3); a test failure goes back with the test reader's short fix brief (`models.test_reader`, Claude Haiku in Claude Code with read-only tools: which cases fail, expected versus got, the file:line to look at) ahead of the raw tail and the full log's path, and with the raw tail alone when the reader fails or times out.
The reader's cost is on the attempt's line (`reader $...`) and in the task's cost.
It runs on the Claude Code subscription, never an API key or OpenRouter: every headless Claude call the CLI makes drops `ANTHROPIC_*` from its environment, so that figure is Claude Code's reference cost, not a bill.
Each clone, and the worktree verify runs in, borrows the main checkout's git-ignored installs (`node_modules` at any depth, `vendor`, `.venv`) as symlinks that never show in `git status`, and trail never edits `.gitignore` there. So install dependencies once in the project worktree before `run`; do not patch test commands to link them.
A repo with a commit convention (type prefixes like `feat:`) declares it once as `commit_convention` in verify.json, `{"types": ["feat", "fix", "chore", "test", "docs", "refactor", "build", "ci"], "example": "feat: add resume upload"}`; every commit the CLI makes and every teammate brief then follows it, and an undeclared one keeps plain messages.
When the build output must match the project worktree byte for byte (a bundler that writes dependency paths into unminified output does not), set `install` in verify.json (for example `bun install --frozen-lockfile`): it runs in each clone and in verify's worktree instead of borrowing, so no checkout shares the project worktree's `node_modules`.
Unset keeps borrowing.
A task whose `files:` names a lockfile borrows nothing: it installs fresh in its own clone, and when it passes that install replaces the project worktree's, so later tasks and verify see the new dependencies.
The trunk is the branch the user is on when you run it (`--trunk` overrides).
That checkout is never switched: clones are separate repos, and every `gh stack` operation runs in a CLI-owned detached worktree under `.compose/<project>/worktrees/.stackroot`; gh stack keeps its state in the repository's shared `.git`, so `gh stack view` works from a task branch there too.
When the run ends, all passed task branches of the project are rebased into one linear chain on the trunk tip, and the chain is cut into review layers registered as one gh stack on the real base (`review_base` in verify.json, else the default branch): `(main) <- <project branch>-layer-01 <- <project branch>-layer-02 <- ...`, printed on a `stack ok` line, with one `layer NN` line each.
Task, test-writer, and layer branches are named `<project branch>-NNN`, `<project branch>-tests-NNN`, and `<project branch>-layer-NN` for every project, but a project with a `fast/<project>/` branch on a remote keeps its `fast/<project>/` names, recorded as `task_prefix` and `layer_prefix` in verify.json until `clean` removes the branches.
A project whose `fast/<project>/` branches were never pushed has them renamed to the new names by its next stack, with every name recorded for them, unless a run of it is live in another process or a new name is taken (a `names` line says which).
Tasks stay tiny for implementers; the layers are sized for the reviewer.
Consecutive tasks, in stack order, are grouped into one layer up to `review_layer_lines` in verify.json (default 300 changed lines), and a task is never split, so a task over the budget is a layer of its own.
A stack opens at most `max_stack_prs` PRs (`~/.compose/config.json`, default 10, `verify.json` overrides), and past it adjacent layers fold into one, same kind first.
Lockfiles (`package-lock.json`, `bun.lock`, `yarn.lock`, `pnpm-lock.yaml`, `go.sum`, any `*.lock`) are not counted, in a layer or in a task's 350 lines; each `layer` line names them and their size, and the size stays on that line, never in the PR body.
The project branch is not a PR: its groundwork commits (scripts, CI, baseline, stubs) become layers of their own, at most the same budget each and never mixed into a task's layer, below the first task layer, and each task's acceptance tests move into its task layer.
A `kind: toolchain` task (2) leads the chain and its layer goes below groundwork, so every layer has the tools the checks run; one that changes a file groundwork changed too stays above it, and `stack  note  toolchain task NNN stays above` names the files.
Layers are rebuilt from the commits on every stack, with the original committer and date, so unchanged layers keep their hashes and a resubmit pushes nothing new.
If the layers would not add up to the task chain's tree, or a commit does not apply in layer order, the CLI says `stack  STOP` and leaves the layer branches and the registered stack as they were; when the project branch is behind its base, the line names the conflicting files and says to rebase the project branch onto it.
A later wave grows the same stack; before it starts, the existing layers are rebased onto the current trunk so new tests and task files are present on every base.
A rebase conflict stops the chain at that layer with the exact commands to resolve it.
`--no-stack` skips that rebase before dispatch and the registration; a task with `after:` still rebases the layers it stacks on.
Use `--only 003,004` for a subset.
Run it in the background (`run_in_background`).
`run`, `verify`, and `resume` work in their own session and log to `results/<command>.log`, which the background task streams; a closed tab or a crashed session ends only that stream, never the work, and `watch` still reports how it ends.
During a run: supervise the teammates and keep Linear true; never type code or poll.
Supervision costs zero tokens while nothing happens:
- Inside herdr you do not start `watch`: your tab's Stop hook (`compose rewake`) parks one each time your turn ends, and its event wakes you as Stop hook feedback.
  Act on it and end your turn; the hook parks the next.
- Outside herdr, start `compose watch --repo <wt> --project <slug>` in the background too.
  It sleeps until something you must act on happens, prints one `event ...` line, and exits; its exit wakes you.
  Act on the line, then start `watch` again.
  Run exactly one `watch` per wake-up, never a loop (`for i in 1 2 3; do compose watch; done` waited 8 minutes on events that had already arrived).
  `watch` has no timeout unless given `--timeout` (a stall event reports silence); it holds a teammate's plain progress report until another event wakes you.
  Never loop on `status` or `herdr agent list` yourself.
- In a session whose harness has no Stop hook or background command that wakes it (Codex), run `compose watch --repo <wt> --project <slug> --timeout 240` in the foreground, act on the line it prints, and run it again.
  An `event timeout` line (exit 2) means nothing happened, so just run it again.
- The event lines, and what you do with each: `task=NNN state=passed` needs nothing from you on Linear (the CLI moved the issue and rolled its parents up); `state=failed` or `state=rejected_*` goes to step 7; `state=contradiction` and `event reflect=...` go to step 8; `agent=<name> status=blocked` means read it and steer; `run=ended` means review the stack; `verify=PASS|FAIL` means report (on PASS the CLI moved the feature to In Review).
  A status line is a wake event, not current state: before a decision, confirm with `compose status` and the result file.
- `crew=<name> skill=stale changed=<files>`: a pi teammate (pi runs no Claude hooks) is working from skill files that changed since it started; relay it with `herdr agent prompt <name> "compose's skill changed since you read it: <files>. Re-read the ones your role uses before acting."`.
- Read before you act: `herdr agent read <slug>-NNN --source recent-unwrapped --lines 80`.
- Steer with one specific instruction: `herdr agent prompt <slug>-NNN "<what to change, which file, which test>"`.
  The CLI's re-prompts and yours go to the same agent: keep yours short and concrete, never contradict the task issue; if the task is wrong, fix it and re-run.
- A stalled agent (working, no output change for a few minutes) gets one nudge, then `compose` times it out into a fresh session by itself; do not kill panes.
- Log each steer as a comment on the task's Linear issue, one line, so the trail is in the ticket and not only in a terminal.
The CLI keeps Linear's state table true on the full path, with the active workspace's Linear key: a dispatched task moves to In Progress, a passed one to In Review with a comment naming its branch, attempts, cost, and model, a failed one stays In Progress with the failure as a comment, and its story and the feature roll up after each change (0s); the run's end and verify PASS roll every story up again from its tasks, so a roll-up one event missed is made true, and verify PASS moves the feature to In Review once every story is. You never move these states or write these comments yourself: you create and edit issues, and write the judgment comments (reviews, decisions, why a task was re-split). Without a key the CLI prints one `linear skipped` line; tell the product owner to run `! pbpaste | compose workspace key <workspace> --linear`, and until then move the states yourself as the table says. Done comes with the merges: `compose clean` moves it (step 7).
Nothing is pushed.
`compose stack --submit` runs `gh stack submit --auto` on the layers, which pushes every branch, opens one draft PR per layer, and links them as a GitHub stack; it then checks each layer has its PR on the layer below (`submit PR #N on <base>`, or `NO PR for <branch>`).
Before anything is pushed, each layer runs the `test` of the tasks it is the lowest layer for, on its own tree.
That is the lowest layer that holds a task's code and every test commit written for it.
It sits above the task's own layer when a test appended to a shared file has to follow an earlier one.
The verify.json `checks` run on the top layer; a lower layer runs only the cheap ones, not a whole suite.
A lower layer that does not define a check's package script yet (bun, npm, pnpm or yarn says the script is missing) skips that check with a `layers later` line, so groundwork below a tool's setup passes when its toolchain task could not go under it; the top runs every check, so a script no layer adds still refuses the submit.
The first failing layer refuses the submit and is named.
A lower layer must not need code from a layer above it: fix it, then submit again.
A command already green on a layer's tree (git tree sha, same command) is not run again.
The layer prints `<check> green on tree <sha12> at <time>, not rerun`.
A red or unknown result is never reused.
A layer whose tree differs from every recorded green tree runs as before.
`--fresh` runs everything.
After a rebase or a stack rebuild, run one full suite on the top of the stack and the final verify, never a suite per layer.
The submit gate already runs, on each layer, the tests of the tasks it is the lowest layer for, and takes what is green.
A failing test that already fails on the stack's base, in a file the stack does not touch, is listed as `layers base` and accepted.
A test that passes on the base and fails on a layer is refused with its id.
So is one the base run cannot tell (a timeout, or a failure naming no test), with a line naming the test.
A commit message that names compose, waves, task ids, or Linear is rewritten as the layers are built (`stack  note` line); `compose reword --project <slug> [--set <sha>=<message>]` lists and rewords layer commits in compose's own worktree and never pushes.
It titles each PR by its change: the feature's title for a one-PR stack, the story's title for a layer that holds one whole story, `Groundwork for <feature title>` for a layer of groundwork only, else from its commits (one commit's subject; the stories' titles when its tasks span several and they fit; else the first task's title or the first groundwork subject plus `and N more tasks` or `commits`), with the Jira key kept and `(i/n)` only when the stack has more than one PR.
A title is at most 72 characters before `(i/n)`, the Jira key included: a longer one is cut at a word and ends in `...`.
It writes a body with `## Why`, `## What changed`, `## How it was tested`, and `## Tickets`, built from the task issues and results with no model call.
`## What changed` is one line per task, its implementing commit's subject with its test commits folded in, and one line per groundwork commit.
`## How it was tested` names each task's test command and each check verify passed, then `compose verify passed`, with no attempt or round counts.
Without `--submit`, `compose stack` prints each layer's title and body as a `pr` line, with no `gh pr` call, so you can read them before you ask for the push.
When the base (`review_base`, else the default branch) is ahead of its upstream, the PRs would carry its unpushed commits: `compose stack` says so in a `stack  WARN` line, and `--submit` stops with exit 1 until the base is pushed or its upstream has them.
Pushing the base is the product owner's call: report it as `needs-user`.
`compose stack --submit` submits the layers below the first task that has not passed and prints a `stack  hold` line naming the rest, which join the stack at the next `--submit`.
A layer whose PR is open and whose tip changed refuses the submit with nothing pushed; `compose stack --submit --update` pushes it with `--force-with-lease`, and only when the user said to push.
After a partial land the layers above are cut on `origin/<base>`, never on a checkout of the base, which is left alone.
Run it only when the user has explicitly asked for that push.
The body's `## Why` is the layer's story titles, at most 400 characters, with `Fixes owner/repo#N` on the layer that completes each GitHub issue the stories or feature name, and `## Tickets` links each task's Linear issue.
After verify passes and before you show the product owner the preview, write each layer's PR text: the generated text above is only the fallback.
Each layer's `pr` line says where its text comes from: `[written: .compose/<slug>/pr/<name>.md]`, or `[generated: write .compose/<slug>/pr/<name>.md]` while that file is missing.
The file is named by what the layer holds (`001-002.md`, `groundwork.md`), so it follows its tasks when layers are renumbered; a file whose tasks were regrouped matches no layer, gets a `pr` line of its own, and is never applied.
It holds three parts and nothing else: `# <title>`, `## Why` (2 to 4 sentences: the problem and why this change, for a reviewer who has not read the tickets), and `## What changed` (a few `- ` bullets at the level a reviewer needs, not one per commit).
compose adds the rest: the Jira key and `(i/n)` on the title, the `Fixes` and `Part of` lines under Why, `## How it was tested`, and `## Tickets`.
A file with anything else (another section, a title over 72 characters with the Jira key, a ticket key or `(i/n)` in the title, an issue line in Why, a line in What changed that is not a bullet) is refused on its `pr` line with the reason, and its layer keeps the generated text.
Re-run `compose stack` until every layer says `written`, then show the preview.
A PR whose text a person edited on GitHub keeps that edit on every later `--submit`, so a file only reaches PRs whose text compose still owns.
In the title and Why, never restate commit subjects or task titles, and never use process words (task, wave, verify, compose), ticket ids, or internal names like layer or groundwork.
A good file:

```markdown
# Keep the toggle's state across page reloads

## Why
Reloading the page reset the dark-mode toggle, so users had to turn it on again on every visit.
This stores the choice in the user's settings and reads it back before the first paint, so the page never flashes the wrong theme.

## What changed
- Save the toggle's state to user settings when it changes
- Apply the saved theme before the first render
```
