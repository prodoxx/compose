### 5. Review
You are the senior engineer over the fast models. Review each layer the moment its `state=passed` event arrives, while the rest of the run continues, not after the run: a task stacked on it starts right away, so a bad layer caught late has been built on.
`run` ends with a `NNN triage clean|flag: <reason>` line per passed task: a fast model checked each diff against its brief and the simplicity bar, all at once (`compose triage` repeats it). Read flagged layers in full. For a clean layer check only its diffstat (`git diff --stat <base>..<project branch>-NNN`): when every changed file is in the task's `files:`, accept it without reading the diff. Reading every diff of an all-clean run is the time triage exists to save. A flag is a pointer, never a verdict.
Read `.compose/<project>/results/NNN.json` and the layer's own diff: `git diff <base>..<project branch>-NNN`, where `base` is in the result (`HEAD` or the lower task's branch). `gh stack view --json` from a layer branch shows the chain.
Passing is not done.
Reject scope creep, gamed tests, site-specific hacks, over-engineering (anything past the plan's simplicity bar), and poor quality; a rejected layer is re-split or fixed, then re-run, and every task stacked on it re-runs on the new layer (`run --only <its id and theirs> --redo`).
Comment the rejection on the task's issue in one paragraph.
Every layer review ends in two verdicts, one line each on the task's issue: the code (accept, or reject with the reason) and the brief (sufficient, or what it lacked: a fact, an interface, a constraint the implementer had to guess).
The brief's verdict is the planner's input for the next cut and for a re-plan (step 8): a gap that recurs across briefs is a planning rule to fix, not a run of rejections.
You never merge, locally or on GitHub.
The layer is the unit a human reviews, so check the `layer` lines too: groundwork and tests land in layers under the budget, and a layer well over it means one task is too big (re-split it).
When the user says so, `compose stack --submit` pushes the stack and opens one draft PR per review layer (each task layer holds its own tests); a human reviewer reads them bottom-up and decides on GitHub whether the stack merges.
`gh stack merge` is the reviewer's tool, not yours.

The first look comes right after `run`, before any full verify: start `compose verify --project <p> --review-only` (the diff review and the acceptance questions, no checks, e2e or fixes; it writes `results/review.json`), and when `verify.json` has `prototype` entries, `compose verify --project <p> --prototype` beside it.
Open `results/prototype.md`, view each reference next to its capture, and tick each line; a line that does not match becomes a task before the first full verify.
Review findings that arrive this early cost one task each, not a fix round after the whole pipeline.
A layer that merged without a review, or one task's change on its own, is reviewed with `compose review --project <p> --only NNN[,NNN]` (each task's diff against the layer it sits on, the reviewer's perspectives and confirm step, findings with file:line, recorded on the task's issue as review evidence for Jev) and a change that is not a task branch with `--range <base>..<tip>`; never import `fc_review` from a script, which skips the key loading.
A confirmed finding that is false is not fixed and not skipped with `--skip-review`: dismiss it with `compose review --project <p> --dismiss <id> --reason "<why it is false>"` (the `id` is printed under each confirmed finding), which is recorded on the ledger and leaves it out of later reviews.
A finding printed as `held` names a file of a lower layer: dismiss it if false, else cut a top task that lists the file; no fix round runs for it.

Verify runs at the top of the stack, in the CLI's worktree, since layers are never merged locally; its fix commits land on the top layer and are reviewed like everything else.
